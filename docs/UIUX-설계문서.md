## 1. 개요

### 1.1. 목적

본 문서는 인문 프로그램 기반 감정 치유 서비스 플랫폼의 태블릿 상담사용 애플리케이션 UI/UX 설계 결과와 그 근거를 기록한다. 문서의 목적은 다음 두 가지다.

- 설계 결정의 근거를 재현 가능한 형태로 보존하여 후속 작업자가 동일 기준으로 미완성 화면을 설계할 수 있도록 한다.
- 확정된 설계 규칙과 미해결 항목을 구분하여, 인수인계 시점의 판단 부담을 줄인다.

본 문서는 설계 결정과 그 근거를 기술하며, 구체적 수치(간격, 크기, 색상값 등)와 디자인 토큰은 다루지 않는다. 해당 값은 Figma를 단독 기준으로 한다.

### 1.2. 범위

**포함 범위**

- 태블릿 상담사용 화면의 UI/UX 설계 결정
- 전역 설계 규칙 및 원칙 위계
- 기존 웹 서비스에 대한 사용성 평가 결과 중 태블릿 설계에 반영된 항목

**제외 범위**

| 항목 | 사유 |
| --- | --- |
| 환자용 화면 (태블릿/모바일) | 본 문서 작성 시점에 미착수. 상담사용 구현이 마무리되는 시점에 병행 착수 예정 |
| 기존 웹 서비스 리뉴얼 | 일정상 제외 |
| 디자인 토큰 및 수치 명세 | Figma 단독 관리 |
| 백엔드 연동 명세 | 설계 범위 외 |

환자용 화면은 구현 대상 화면 수가 적고, 상담사용에서 확정된 설계 문법(3장 전역 규칙)을 그대로 이어받는다. 따라서 상담사용 구현이 마무리되는 시점에 병행 착수한다. 착수 시 재검토가 필요한 결정은 6.3절에 정리한다.

> **확인 필요:** 상담사용 단독 구현으로 범위가 축소됨에 따라, 기존에 검토하던 단일 기기 이중 사용자(상담사–환자 화면 공유) 구조는 본 문서 범위에서 제외한다. 다만 **감정평가의 설문 수행 화면 한 곳은 예외로 유지된다** — 상담사용 앱 안에서 환자가 직접 태블릿을 조작하는 유일한 지점이다. 4.0.1절 및 4.6.2절 참조. 그 외에 이중 사용자 구조를 전제로 도출되었던 설계 결정(예: 환자 대면 상황에서의 타 환자 정보 노출 방지)은 재검토가 필요하다. 6.2절 6번 항목 참조.

## 2. 설계 기준

### 2.1. 설계 원칙 위계

#### 2.1.1. 위계 정의

설계 결정 간 충돌이 발생할 경우 다음 순서로 우선한다.

**Safety and Trust > Minimalism > Consistency > Motion and Friction > Efficiency > Experience**

| 순위 | 원칙 | 내용 |
| --- | --- | --- |
| 1 | Safety and Trust | 임상 데이터의 무결성과 사용자의 오조작 방지. 데이터 소실·오입력을 유발하는 설계는 다른 어떤 이점으로도 정당화되지 않음 |
| 2 | Minimalism | 화면에 노출되는 요소를 판단에 필요한 최소로 유지 |
| 3 | Consistency | 동일 의미의 요소는 전 화면에서 동일한 형태·위치·동작을 가짐 |
| 4 | Motion and Friction | 중요도에 비례하는 마찰을 부여. 되돌릴 수 없는 조작에는 의도적 마찰을 둠 |
| 5 | Efficiency | 반복 작업의 조작 횟수·이동 거리 최소화 |
| 6 | Experience | 위 항목을 침해하지 않는 범위에서의 심미성·만족도 |

#### 2.1.2. 원칙 충돌 시 판단 절차

1. 충돌하는 원칙을 식별한다.
2. 위계상 상위 원칙을 우선한다.
3. 하위 원칙의 손실이 큰 경우, 상위 원칙을 침해하지 않는 대안을 탐색한다.
4. 대안이 없으면 상위 원칙을 채택하고, 포기한 하위 원칙의 손실을 4장 해당 케이스의 "거부된 대안"에 기록한다.

**사례 A — 배치 확정의 확인 모달 (Safety and Trust > Efficiency)**

환자를 꾹 눌러 시간 슬롯에 놓는 순간 일정을 확정하면 조작 횟수가 최소가 된다(Efficiency). 그러나 드래그는 손가락 위치에 의한 오조작 가능성이 높고, 확정된 일정을 되돌릴 경로가 아직 없다. 3단계에 따라 "상위 원칙을 침해하지 않는 대안"을 탐색한 결과 **놓는 즉시 확정하지 않고 확인 모달을 거치는** 안을 채택했다. 잃은 것은 탭 1회이며, 이 손실은 4.1절 "거부된 대안"에 기록되어 있다.

**사례 B — 지난 시간 행의 시각적 억제 (Safety and Trust > Experience)**

지난 시간대를 `opacity`로 낮추는 것이 시각적으로는 가장 자연스럽다(Experience). 그러나 opacity는 배경과 글자를 함께 씻어내 명도 대비가 기준 미달로 떨어진다 — 실측 결과 `opacity-40`에서 제목 4.44 · 메타 2.99, `opacity-80`에서도 4.68이 한계였다. 임상 정보의 판독 가능성은 Safety and Trust에 해당하므로, **opacity 대신 배경 토큰만 교체**하는 대안을 채택했다(실측 제목 7.21 · 메타 7.21 · 시간 7.75). 3.1절 및 4.1절 참조.

> 사례를 계속 축적한다. 위계 목록만으로는 후속 작업자가 "무엇이 충돌인지" 판별하기 어렵다.

### 2.3. 태블릿 전환 시 제약 조건

#### 2.3.1. 터치 인터랙션 제약

기존 웹은 마우스 입력을 전제로 설계되었으며, 터치 입력으로의 전환은 다음 차이를 발생시킨다.

- **포인팅 정밀도 저하** — 좁은 클릭 반경에 의존하는 요소는 오조작 가능성이 높아진다. → 3.3절 터치 타겟 규격
- **hover 상태 부재** — 마우스 오버로 제공되던 사전 피드백이 성립하지 않으므로, 선택·활성 상태를 명시적으로 표현해야 한다. → 3.8절 pressed 피드백 규칙
- **손에 의한 가림** — 조작 지점 아래 영역이 가려지므로, 조작 결과가 나타나는 위치를 조작 지점 상단 또는 별도 영역에 배치해야 한다. → 4.1절 팝오버 배치(행 왼쪽), 4.2절 캘린더 팝오버 배치(칸 오른쪽)

#### 2.3.2. 화면 방향 및 해상도

- **방향:** 랜드스케이프 고정. 좌측 내비게이션과 우측 패널을 동시 노출하는 3분할 구조가 세로 방향에서 성립하지 않음.
- **대상 기기:** Samsung Galaxy Tab S11 Ultra
- **논리 해상도:** `[실측 후 기입]` (현재 1138×712 추정값 사용)

> **확인 필요:** 논리 해상도는 실기기 미확보 상태로 추정값에 의존하고 있다. 실측 후 확정한다. 다만 설계 및 구현 모두 고정 픽셀 높이에 의존하지 않는 방식으로 진행하고 있어, 실측값 확정 시 수정 범위는 제한적일 것으로 예상된다.
>
> 추정 근거: 712에는 상태바와 제스처바(합 61)가 포함되며, Figma 셸 콘텐츠 높이는 603이다. PWA standalone 뷰포트는 시스템 UI를 제외하므로 `100dvh`는 약 651이 되고, 외곽 패딩을 제하면 603이 자연히 도출된다. 따라서 **603을 고정값으로 하드코딩하지 않는다.** 실기기에서 `innerHeight`가 651 근처인지만 확인하면 확정된다.

#### 2.3.3. 배포 형태에 따른 제약

주소창이 없는 PWA standalone 모드로 배포한다. 이로부터 다음 제약이 파생된다.

- 브라우저 뒤로가기·새로고침이 존재하지 않으므로, **앱 내 이탈 경로가 항상 존재해야 한다.**
- Android 제스처 뒤로가기가 `history.back()`으로 연결되므로, **모달은 history 엔트리로 등록해야 한다.** 등록하지 않으면 모달이 열린 상태에서 뒤로가기가 화면 자체를 이탈시킨다.
- 미저장 경고는 라우터 가드와 뒤로가기 이벤트 **양쪽 모두**에 걸어야 한다. 한쪽만 걸면 나머지 경로로 데이터가 소실된다(Safety and Trust).

## 3. 전역 설계 규칙

### 3.1. 색상 운용 규칙

**Accent 용법은 3가지로 동결한다.**

| 용법 | 예 |
| --- | --- |
| 선택 상태 | 캘린더 선택 칸, 팝오버가 열린 아젠다 행, 분석 화면의 선택된 막대 |
| 현재 위치 마커 | 아젠다의 '진행 중' 배지, 프로세스 스테퍼의 진행 중 노드 |
| 드롭 대상 | 배치 중 놓을 수 있는 슬롯 |

**선택 상태는 배경만으로 표현하지 않는다.** 선택 배경은 흰 표면과의 명도 차가 작아, 배경만 두면 선택되었는지가 잘 읽히지 않는다. 테두리(또는 inset ring)를 accent로 함께 올려 두 신호가 같이 움직이게 한다. 자리를 차지하면 안 되는 곳(캘린더 칸)에서는 border 대신 inset ring을 쓴다(4.2.1절).

그 외 용도의 사용을 금지한다. Accent가 세 가지 의미만 갖기 때문에 화면 어디에서 마주쳐도 해석이 즉시 가능하다. Figma 원안에서 accent로 고정되어 있던 요소(전체 환자 리스트의 `필터` 버튼 등)도 이 세 용법 중 하나로 해석되지 않으면 중립색으로 되돌렸다.

**경고 색상은 악화(deterioration) 표현에만 사용하며, 개선 표현은 중립색으로 처리한다.** 개선과 악화를 모두 유채색으로 처리할 경우 화면 내 유채색 비중이 높아져 Accent의 변별력이 떨어진다. 적용 결과:

- 기한이 지난 **미완료** 작업 → 경고색 (`N일 지남`)
- 다음 일정이 없는 환자 → 경고색 + dot (잡아야 할 것이 남았다는 뜻)
- 작업 **완료** → 체크 + 중립색. 완료는 개선이므로 경고색을 쓰지 않는다
- 완료된 작업의 지난 날짜 → 경고색 없음. 지난 날짜여도 악화가 아니다

**파괴적 조작의 컨트롤은 danger 토큰을 쓴다.** 악화 표현과는 다른 자리다 — 악화는 '상태가 나빠졌다'는 서술이고, 이쪽은 '누르면 없어진다'는 예고다. 특히 **아이콘만 있는 삭제 버튼은 색이 유일한 신호**라 중립색으로 두면 다른 아이콘 버튼과 구별되지 않는다. 삭제 조작은 색과 확인 모달(3.6절)을 **함께** 갖춘다 — 색만 있으면 실수를 되돌릴 수 없고, 확인만 있으면 누르기 전에 알 수 없다.

**파괴적 문법은 전 화면에서 같은 색이다.** 아이콘만 있는 삭제 버튼 · 테두리 삭제 버튼 · 삭제 확인 모달의 확정 버튼 · 미저장 경고의 `나가기 (저장 안 함)`까지 같은 계열을 쓴다. 자리(가장자리로 떼어놓기 · 테두리만 두기)로 세기를 낮추더라도 **색은 낮추지 않는다** — 자리만으로는 '무엇이 사라지는 쪽인가'가 보이지 않는다. 채워진 삭제 버튼을 위해 `danger-fill` · `danger-fill-pressed` · `text-on-danger` 토큰을 더했고, **이 셋은 다크에서 재매핑하지 않는다**(흰 글자를 얹는 자리라 밝히면 대비가 무너진다).

**색상은 2레이어 토큰 시스템으로 관리한다.**

| 레이어 | 내용 | 화면 코드에서의 사용 |
| --- | --- | --- |
| Layer 1 Primitives | `--color-neutral-*`, `--color-brand-*` 등 원색 스케일 | **직접 사용 금지** |
| Layer 2 Semantic | `surface-card`, `text-primary`, `border-subtle` 등 역할 이름 | 화면 코드는 이것만 사용 |

다크 모드는 `.dark`에서 Semantic 토큰만 재매핑한다. 화면 코드에 `dark:` 분기를 쓰지 않으므로 다크 대응 누락이 구조적으로 발생하지 않는다. Figma 스케일에 없는 값이 필요하면 **구간의 중간값을 새 Primitive로 만들고 반드시 Semantic 토큰을 붙인다.** 화면 코드에 임의 색상값이 들어가는 것을 막기 위함이다.

### 3.2. CTA 문법

| 요소 | 의미 |
| --- | --- |
| 탭 | 탐색 / 조회. 상태를 변경하지 않음 |
| 버튼 | 결정. 상태를 변경하거나 다음 단계로 진행함 |

전 화면에 적용되는 전역 규칙이다. 프로세스 화면의 주 행동은 우하단 고정 Primary 버튼으로 통일하며, 사전 조건 미충족 시 비활성 상태로 표시한다.

확인·확정 버튼은 반전 표면(`surface-inverse` + `text-inverse`)을 사용한다. 라이트에서 검정, 다크에서 흰색으로 자동 반전되므로 두 모드 모두에서 최대 대비를 갖는다. 브랜드 채움색을 쓰지 않는 이유는 3.1절 accent 용법 동결 때문이다.

### 3.3. 터치 타겟 규격

- 하드 플로어: 44px. 어떤 경우에도 이보다 작은 터치 타겟을 두지 않는다.
- 기본값: 48px.
- 히트 에어리어와 시각적 경계의 분리를 허용한다. 시각 요소가 44px 미만이더라도 히트 에어리어가 기준을 충족하면 된다.

분리 허용의 실제 적용: 모달의 확정·취소 버튼은 시각 높이 36 · 터치 높이 44다. 분석 화면의 막대 그래프는 막대 자체가 얇지만 히트 영역이 행/칸 전체(가로 250×44, 세로 44×145)이며 트랙의 빈 부분까지 포함한다.

### 3.4. 표면 분리 및 계층 표현

표면 간 분리는 그림자를 사용하지 않고 border로만 처리한다. 다크 모드에서 그림자에 의한 계층 표현이 성립하지 않기 때문이다.

**표면 계단**은 라이트·다크 양쪽에서 같은 방향을 유지한다.

| 위치 | 평소 | 지난 시간 |
| --- | --- | --- |
| 행 | card | recessed |
| 행 위의 블록 | container | canvas |

`recessed`는 `container`보다 **반 단계** 아래다. 한 단계를 통째로 내리면 블록과의 간격이 사라져 띠가 뭉갠다.

라운드 위계는 **셸 패널 16 → 화면 내부 카드 8**로 구분한다. 모달 내부에서는 **카드 16 → 그 안은 전부 8**이며, 리스트는 컨테이너 하나(8, border)로 묶고 행은 라운드 없이 구분선으로만 나눈다. 라운드 8짜리 요소는 전부 1px border를 갖는다.

### 3.5. 오버레이 규칙

| 콘텐츠 성격 | 형태 | dismiss | history 엔트리 |
| --- | --- | --- | --- |
| 무거운 콘텐츠 (다단계 입력, 상세 편집) | 대형 모달 | 뒤로가기 전용 | 생성함 |
| 가벼운 콘텐츠 (선택, 요약 조회) | 팝오버 | 외부 탭 | 생성하지 않음 |

중요 작업 모달은 외부 탭 dismiss를 금지한다. 의도치 않은 닫힘으로 입력값이 소실되는 것을 방지하기 위함이다(Safety and Trust).

**모달 history는 반드시 라우터를 거친다.** 열 때 쿼리를 push하고, 닫을 때 `router.back()`하며, 쿼리가 사라지면 닫는다. `history.pushState`로 직접 엔트리를 만들면 라우터가 모르는 엔트리가 생기고, 뒤로가기의 popstate를 라우터가 화면 이동으로 처리해 다른 화면으로 튕긴다. 이 처리는 **모달 셸 한 곳에만** 둔다 — 모달마다 다시 구현하면 한쪽만 틀어진다(Consistency).

팝오버가 열린 원본 행/칸은 **선택 상태**로 표시한다. 목록을 보는 동안 어디에서 열렸는지 잃지 않기 위함이며, 3.1절 accent 용법 '선택 상태'에 해당한다.

### 3.6. 저장 상태 및 데이터 보호 규칙

- 오토세이브를 전제하지 않는다. 저장은 명시적 조작으로만 발생한다.
- 미저장 상태에서 이탈이 발생할 경우 경고 모달을 표시한다. 모달은 비파괴적 선택지를 우선 배치한 3버튼 구조를 따른다(Figma `186:6839`).
  - 선택지는 `나가기 (저장 안 함)` / `계속 작성` / `저장하고 나가기` 셋이다.
  - **파괴적인 선택지만 텍스트로 두고 반대편 끝에 떼어놓는다.** 나머지 둘은 버튼으로 우측에 묶인다. 셋을 나란히 놓으면 파괴적인 쪽을 잘못 누른다
  - 무엇이 사라지는지를 문구가 특정한다. 화면마다 대상만 갈아끼우고 틀은 공유한다
- 푸터에는 저장 상태와 마지막 저장 시각을 병렬 표시한다. 시각 표기에는 "마지막 저장" 레이블을 반드시 부기한다. 레이블이 없으면 저장 완료 상태와 시각적으로 혼동된다.
- **되돌리기는 시간 제한이 있는 실행취소(스낵바)로 제공하지 않는다.** 명시적 편집·삭제 경로로 제공한다. 시간 제한 실행취소는 "저장은 명시적 조작으로만" 원칙과 어긋나며, 놓치면 복구 경로가 사라진다.
  - **편집은 새로 만드는 것이 아니라 옮기는 것이다.** 같은 일정을 옮길 때는 대상(누구와 만나는가)을 바꾸지 않는다. 대상을 바꾸는 것은 지우고 새로 잡는 일이지 같은 약속을 고치는 일이 아니다.
  - **편집 화면은 추가 화면과 같은 폼을 쓴다.** 시간 선택지가 드롭 규칙과 같아야 하고(4.0.4절), 중복 경고도 같이 타야 하기 때문이다. 폼을 따로 만들면 규칙이 한쪽에만 남는다.
  - 다만 **편집 중인 일정은 자기 자신을 막지 않는다.** 자기가 점유한 시간과 날짜가 후보에서 빠지면 "날짜는 그대로 두고 시간만 옮기기"가 불가능해지고, 중복 검사에도 자기 자신이 걸린다.
- 되돌리기가 불가능한 조작(삭제 등)은 확인 모달을 반드시 거치고, 문구에 복구 불가를 명시한다.
  - **내용이 없는 줄은 확인 없이 지운다.** 잃을 것이 없는데 모달을 띄우면 빈 줄 하나 지우는 데 두 번 눌러야 한다.
- **`나가기 (저장 안 함)`은 초안을 되돌린 뒤 이동해야 한다.** 되돌리지 않고 이동만 시키면 라우터 가드가 여전히 '변경됨'으로 보고 다시 막아, 경고만 되풀이되고 버튼이 죽은 것처럼 보인다.

### 3.7. 파생 데이터 산출 규칙

**같은 사실을 두 곳에 저장하지 않는다.** 한쪽만 갱신되면 두 화면이 갈라지기 때문이다(Safety and Trust). 현재 적용된 파생 관계:

| 파생 대상 | 원본 | 사유 |
| --- | --- | --- |
| 타임라인의 업무 블록 | 작업 목록 | 완료 상태가 두 곳에 생기는 것을 막는다 |
| 환자의 마지막 진료 · 다음 일정 | 일정 데이터 | 환자 레코드에 적어두면 배치할 때마다 갱신해야 한다 |
| 분석 화면의 모든 집계 | 환자 명단 | 별도 집계 목업을 두지 않는다 |
| 우측 패널의 최근 환자 | 환자 명단 | 동일 |

**일정은 환자의 현재 상태를 참조하지 않는다.** 일정 이벤트는 "그때 무엇을 했는지"를 자기가 들고 있고, 환자는 "지금 어디까지 왔는지"와 "다음에 할 것"을 갖는다. 따라서 같은 환자라도 날짜에 따라 다른 단계가 기록될 수 있으며, 아젠다와 환자 패널은 1:1 대응이 아니다.

### 3.8. 상태 피드백 규칙

hover가 없는 터치 환경에서는 **누를 수 있는 것은 누르는 동안 표면이 바뀌어야 한다.** 반응이 없으면 눌렀는지 알 수 없고, 이는 고장으로 읽힌다.

| 대상 | pressed 처리 |
| --- | --- |
| 일반 요소 (card·container·recessed·canvas 어느 표면이든) | 단일 pressed 표면으로 통일 |
| 선택된 요소 | 선택 상태 전용 pressed (accent를 잃지 않는다). **브랜드 스케일 한 단계만 내려간다** — 두 단계를 내리면 눌린 순간 색이 확 진해져 '눌렸다'가 아니라 '다른 상태로 바뀌었다'로 읽힌다. 한 단계 폭은 일반 pressed와 같고, 다크에서도 같은 한 단계다 |
| 채워진 버튼 | 반전 표면의 pressed |
| 텍스트만 있는 버튼 | 배경 대신 글자색을 올린다 |
| 지난 시간의 행·블록 | 한 단계 더 강한 pressed (평소 표면이 pressed와 값이 같아 변화가 보이지 않기 때문) |

- 평소 표면이 무엇이든 pressed는 **한 값으로 통일**한다. 라이트에서는 어두워지고 다크에서는 밝아지지만, 어느 쪽이든 네 표면 모두와 다른 값이라 항상 보인다.
- **행과 그 안의 블록에 함께 건다.** 눌린 동안 행 전체가 한 색 띠로 보여야 하며, 블록만 더 어두우면 "박스가 눌린 것"으로 읽힌다.
- 카드 위의 요소도 일반 pressed를 쓴다. 카드 전용 pressed는 카드와 한 단계밖에 차이가 없어 눌린 것이 거의 보이지 않는다.
- **드래그 중에는 pressed를 넣지 않는다.** 드롭 상태(가능·불가) 표현과 겹친다.
- 평소 `opacity`가 낮게 깔린 요소(캘린더의 인접 달 칸)는 누르는 동안 opacity를 걷어낸다. 그러지 않으면 눌린 색까지 함께 씻긴다.

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 지난 시간 행은 평소 표면이 일반 pressed와 값이 같아 눌러도 변화가 없다. 블록만 한 단계 더 내리면 변화는 보이지만, 행보다 블록이 어두워 **'박스가 눌린 것'** 으로 읽힌다 |
| 위반 원칙 | Consistency — 지나지 않은 행은 행과 블록이 같은 색이 되어 '행 전체가 눌린 것'으로 읽히는데, 같은 제스처가 두 가지로 읽힌다 |
| 변경 전 | 행은 일반 pressed, 블록만 한 단계 강한 pressed |
| 변경 후 | **지난 행은 행과 블록을 함께 한 단계 강한 pressed로 내려** 한 색 띠를 만든다. 평소의 표면 계단(행/블록이 다름)은 유지되고, 눌린 순간에만 한 색으로 합쳐진다 |
| 거부된 대안 | 블록만 강하게 — 위 문제. / 지난 행에 pressed를 걸지 않음 — 반응 없는 요소는 고장으로 읽힌다 |
| 검증 상태 | 내부 검토 (DOM 실측 확인) |

**비활성 요소를 눌렀을 때는 이유를 말한다.** 아무 반응이 없으면 고장으로 읽힌다. 지난 시간·지난 날짜를 누르면 비활성 사유 콜아웃이 팝오버 자리에 표시된다(Figma `176:5336`).

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 콜아웃이 한 줄이었다. 무엇이 막혔는지는 알려주지만 **언제 풀리는지**를 말하지 않아, 사용자가 다음에 무엇을 해야 할지 모른다 |
| 위반 원칙 | Safety and Trust — 막힌 이유를 모르면 조작을 반복하게 되고, 그 반복이 고장으로 읽힌다 |
| 변경 전 | 아이콘 + 한 줄 문구. 라운드 16, 경고색은 amber 계열, 글자는 본문색 |
| 변경 후 | **두 줄이다.** 첫 줄이 무엇이 안 되는지, 둘째 줄이 언제 되는지를 말한다. 첫 줄만 경고색이고 둘째 줄은 중립색이다. 라운드는 화면 내부 카드와 같은 값으로 내리고, 경고색은 기한 지난 작업과 같은 지표색 계열로 통일했다 |
| 거부된 대안 | 둘째 줄도 경고색 — 덩어리 전체가 경고로 읽혀 정작 해법인 둘째 줄이 묻힌다. / 한 줄 유지 + 문구만 길게 — 한 문장에 두 가지 정보가 섞여 훑어 읽을 수 없다 |
| 검증 상태 | 내부 검토 (DOM 실측이 Figma 규격과 일치. 아젠다·캘린더 양쪽 확인) |

콜아웃은 **문구 길이에 맞춰 줄어든다.** 같은 자리에 뜨는 목록 팝오버만 고정 폭이다 — 짧은 문구를 넓은 상자에 넣으면 빈 자리가 무엇인가 빠진 것처럼 읽힌다.

### 3.9. 모션 규칙

> **확인 필요:** 아래는 Figma 프로토타입이 정의되지 않아 잠정 합의한 값이다. 프로토타입 확정 시 교체한다.

- easing은 단일 값으로 통일한다.
- duration은 3단계로 고정한다: **상태 피드백 / 드롭 타깃·명도 전환 / 위치 이동**. 화면 코드에 임의 duration을 쓰지 않고 이 3단계로 흡수한다.
- 꾹 누르기 임계 시간과 이동 허용 오차는 상수로 관리한다.

## 4. 화면별 설계 결정

각 화면의 설계 결정은 다음 템플릿으로 기술한다.

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 어떤 상황에서 무엇이 문제였는가 |
| 위반 원칙 | 2.1절 위계 중 해당 항목 |
| 변경 전 / 후 | 기존 처리와 변경된 처리 |
| 거부된 대안 | 검토했으나 채택하지 않은 안과 그 사유 |
| 검증 상태 | 미검증 / 내부 검토 / 실기기 확인 / 사용자 확인 |

### 4.0. 화면 구조 공통

#### 4.0.1. 셸의 3분할과 우측 패널의 유무

**화면은 무엇을 다루느냐로 갈리며, 우측 환자 패널의 유무가 여기서 정해진다.**

| 갈래 | 화면 | 좌측 내비 | 우측 환자 패널 |
| --- | --- | --- | --- |
| **환자**를 다룬다 | 홈(업무) · 일정 · 환자 분석 | 있다 | 있다 |
| **프로그램/프로세스**를 다룬다 | 효과성 분석 · 저작도구 | 있다 | 없다 |
| **환자 자체가 본문**이다 | 전체 환자 리스트 · 환자 상세 | 있다 | 없다 |
| **환자가 직접 조작한다** | 감정평가 설문 수행 | **없다** | **없다** |

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 전체 환자 리스트와 환자 상세는 환자를 다루는 화면이므로 위 규칙대로면 우측 패널을 가져야 하지만, 화면 자체가 패널이 하던 일을 더 넓게 수행한다 |
| 위반 원칙 | Minimalism — 같은 정보가 한 화면에 두 번 노출됨 |
| 변경 후 | 라우트 메타 플래그가 셸에서 패널을 걷고 중앙 패딩도 함께 줄인다 |
| 거부된 대안 | 화면별로 패널을 개별 제어 — 화면이 늘어날 때마다 누락이 발생하므로 라우트 선언으로 일원화 |
| 검증 상태 | 내부 검토 |

패널의 환자를 탭하면 환자 상세로 이동한다. 꾹 누르기는 배치 조작이므로 그대로 유지된다.

**네 번째 갈래는 사용자가 바뀌는 유일한 지점이다.** 감정평가의 설문 수행 화면에서는 상담사가 태블릿을 환자에게 건네고 환자가 직접 응답한다. 이 화면은 환자를 다루는 화면이므로 위 규칙대로면 우측 패널을 가져야 하지만, **좌측 내비게이션과 우측 환자 패널이 모두 감춰진다.**

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 설문 응답 중에는 태블릿의 조작자가 상담사가 아니라 환자다. 셸이 그대로 노출되면 (1) 우측 패널에 다른 환자의 이름·상태가 보이고, (2) 좌측 내비게이션으로 환자가 임의의 화면에 진입할 수 있다 |
| 위반 원칙 | Safety and Trust — 타 환자 정보 노출은 임상 정보 보호 위반이며, 응답 중 이탈은 데이터 소실로 이어진다 |
| 변경 전 | 모든 화면이 3분할 셸을 유지 |
| 변경 후 | **설문 수행 화면에서만 셸 전체(좌측 내비 + 우측 패널)를 걷고 본문이 화면을 채운다.** 조작 주체가 환자인 동안 상담사용 탐색 경로 자체를 없앤다 |
| 거부된 대안 | 우측 패널만 감춤 — 좌측 내비로 이탈이 가능해 응답이 소실된다. / 별도 잠금 모드 오버레이 — 셸이 남아 있어 타 환자 정보가 계속 렌더되며, 해제 조작을 환자가 발견할 수 있다 |
| 검증 상태 | 미검증 (설계 확정, 화면 미착수) |

이 갈래는 4.0.1절의 라우트 메타 플래그로 함께 선언한다. 화면별 개별 제어를 두지 않는 이유는 위와 같다 — 누락 시의 손실이 가장 큰 화면이기 때문에 더욱 선언으로 일원화한다.

**차단은 UI 경로 제거까지이며, 기기 수준의 잠금은 전제하지 않는다.** 다만 Android 제스처 뒤로가기는 UI와 무관하게 살아 있으므로, **설문 화면에서 뒤로가기가 발생하면 경고 모달을 띄운다.** 2.3.3절의 "미저장 경고는 라우터 가드와 뒤로가기 이벤트 양쪽 모두에 건다" 규칙이 여기에 그대로 적용된다.

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 셸을 걷어도 제스처 뒤로가기는 남는다. 환자가 실수로 뒤로 스와이프하면 응답이 소실된다 |
| 위반 원칙 | Safety and Trust |
| 변경 후 | **뒤로가기 시 경고 모달.** 3.6절의 미저장 이탈 경고와 같은 문법이다 |
| 거부된 대안 | 기기 화면 고정(Android Screen Pinning) 전제 — 앱이 제어할 수 없는 시스템 설정에 안전성을 의존하게 된다. 상담사가 매번 켜야 하고, 켜지지 않은 채로 건네지면 방어가 전혀 없다. / 뒤로가기 무반응 — 반응 없는 조작은 고장으로 읽힌다(3.8절) |
| 검증 상태 | 미검증 (설계 확정, 화면 미착수) |

#### 4.0.2. 행 인터랙션 문법 (탭 / 꾹 누르기)

같은 행이 두 제스처를 모두 받는다.

| 제스처 | 의미 |
| --- | --- |
| 탭 | 상세 열기 (탐색 — 3.2절) |
| 꾹 누르기 | 배치 (결정 — 3.2절) |

배치로 끝난 제스처의 click은 캡처 단계에서 한 번 삼킨다. 다만 **손을 뗀 자리가 누른 자리와 다르면 click이 아예 발생하지 않으므로**, 삼킴 플래그가 남아 다음 탭을 잘못 삼킬 수 있다. 이를 막기 위해 제스처 시작 시점마다 플래그를 해제한다 — 두 처리는 분리할 수 없는 짝이다.

| 행 | 탭의 결과 |
| --- | --- |
| 작업 목록의 행 | 작업 상세 (설명 · 완료) |
| 아젠다의 업무 블록 | 작업 상세 |
| 아젠다의 환자 블록 | 환자 상세 |
| 아젠다의 빈 행 | 그 시간으로 일정 추가 |
| 캘린더 팝오버의 업무 행 | 작업 상세 (팝오버를 먼저 닫아 모달만 history 엔트리를 갖게 한다) |

**환자 블록의 탭은 일정 상세로 간다.**

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 배치한 환자 일정을 지우거나 고칠 길이 없었다. 그런데 타임라인 블록의 두 제스처는 이미 차 있다 — 탭은 환자 상세로, 꾹 누르기는 배치로 |
| 위반 원칙 | Safety and Trust — 되돌릴 수 없는 조작이 남는다. Consistency — 작업 블록은 탭이 조작 자리(작업 상세)로 가는데 환자 블록만 화면 밖으로 나간다 |
| 변경 전 | 환자 블록 탭 → 환자 상세 화면 |
| 변경 후 | **환자 블록 탭 → 일정 상세 모달.** 작업 블록이 작업 상세로 열리는 것과 같은 문법이 된다. 편집·삭제가 이 모달에서 갈라지고, 환자 상세로 가는 길은 모달 안의 행으로 남는다 |
| 거부된 대안 | 블록에 편집·삭제 아이콘 상시 노출 — 모든 환자 블록에 아이콘 두 개가 항상 보여 타임라인이 시끄러워지고, Figma 근거도 없다(Minimalism). / 캘린더 팝오버에서만 편집·삭제 — 확정 규칙은 지켜지지만 아젠다에서 일하는 동안에는 되돌릴 길이 없다 |
| 검증 상태 | 내부 검토 (아젠다·캘린더 양쪽에서 상세 → 편집 → 이동 → 삭제 동작 확인) |

환자 상세로 가는 진입 경로는 넷에서 줄지 않는다 — 일정 상세 모달의 행 · 캘린더 팝오버 · 전체 환자 리스트 · 우측 환자 패널.

#### 4.0.3. 배치(드래그 앤 드롭) 문법

| 상태 | 표현 |
| --- | --- |
| 놓을 수 있음 | 선택 배경 + 점선 테두리 + accent 바, 시간 라벨 강조 |
| 놓을 수 없음 | 행 전체 opacity 저하 + 위험 배경 + 실선 테두리 |

- **환자는 빈 행에만** 놓을 수 있다. 그 시간에 그 환자를 만나는 일이므로 겹칠 수 없다.
- **작업은 다른 작업 위에 겹칠 수 있다.** 환자 일정이 있는 행만 막힌다.
  - 원안은 "일정이 있는 행은 드롭 대상이 될 수 없다"였다(Figma에 채워진 행의 drop-active 변형이 없다는 것이 근거). 완료된 작업이 그 시간을 영구히 점유하는 문제 때문에 작업에 한해 풀었다.
  - > **확인 필요:** 채워진 행의 drop-active 표현은 Figma 근거가 없는 초안이다.
- 손가락이 특정 슬롯 위에 있으면 **그 슬롯만 남기고 나머지 후보를 흐린다.** 아직 어느 슬롯 위도 아니면 후보를 모두 같은 세기로 보여준다.
- 빈 행의 블록도 **항상 렌더**한다(평소엔 투명). 조건부로 새로 붙이면 전환 없이 즉시 나타나 색 전환을 거치는 다른 행보다 빨라 보인다(Consistency).
- **놓는 즉시 확정하지 않는다.** 확인 모달을 거친다 — 3.6절 오토세이브 없음 규칙의 연장.
- **놓을 수 없는 자리에 놓으면 이유를 말한다.**

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 드래그하는 동안에는 막힌 자리가 붉게 표시되지만, 손을 떼는 순간 그 표현이 통째로 사라진다. 아무 일도 일어나지 않아 조작이 먹히지 않은 것처럼 보인다 |
| 위반 원칙 | Safety and Trust — 반응 없는 조작은 고장으로 읽히고, 사용자는 같은 조작을 반복한다 |
| 변경 전 | 손을 떼면 드롭 표현만 사라지고 끝 |
| 변경 후 | **손 뗀 자리에 비활성 사유 콜아웃**(3.8절)이 뜬다. 막힌 이유마다 문구가 다르다 — 지난 시간 / 이미 일정이 있음 / 작업이 환자 일정 위에 놓임 / 지난 날짜 / 빈 시간이 없는 날 |
| 거부된 대안 | 드롭 자체를 무시 — 위 문제 그대로. / 확인 모달을 띄워 거절 — 되돌릴 것이 없는 알림에 모달은 과한 마찰이다(Motion and Friction) |
| 검증 상태 | 내부 검토 (다섯 경우 중 아젠다 두 가지·캘린더 지난 날짜를 포인터 이벤트로 확인) |

막힌 자리도 **드롭 대상과 함께 표시를 달고 있어야 한다.** 놓을 수 있는 자리만 표시하면 '막힌 자리'와 '아무것도 없는 빈 화면'을 구분할 수 없어 빗나간 드롭에도 경고가 뜬다.
- 같은 날 같은 대상이 이미 있으면 **중복 경고**를 거친다.

**캘린더에서의 드롭 단위는 날짜다.** 지난 날이거나 빈 시간이 하나도 없으면 놓을 수 없다. 시간은 확인 모달에서 고르며, 그 날의 빈 시간만 선택지로 나온다. 드롭으로 열린 모달은 **시간 기본값을 채우지 않는다** — 고르지 않은 시간에 확정되면 안 되기 때문이다(Safety and Trust).

#### 4.0.4. 모달 공통

배치 확인 · 일정 추가 · 작업 추가 · 작업 상세가 **하나의 셸을 공유한다.** history 처리도 셸에 있다(3.5절).

- 시간 선택지는 **드롭 가능 규칙과 동일**하다(비어 있고 지나지 않은 시간). 규칙이 갈라지면 드래그로는 막히는 자리가 모달로는 뚫린다.
- **날짜가 정해지지 않은 경로에서는 날짜를 먼저 고른다.** 날짜를 바꾸면 그 날의 빈 시간으로 목록이 갱신되고 시간 선택은 초기화된다.
- 환자 리스트는 **우측 환자 패널과 같은 구조**다(최근 환자 → 전체 환자). 검색 중에는 두 구간을 합쳐 하나로 보여준다.
- **중복 경고의 취소는 모달을 닫지 않는다.** 고르던 폼으로 돌아간다. 닫으려면 스크림 탭이나 뒤로가기를 쓴다 — 경고 하나 때문에 입력이 통째로 사라지면 안 된다(Safety and Trust).
- 모달은 화면을 넘기지 않고 본문만 스크롤하며, 버튼은 하단에 고정한다.

**짧은 확인은 alert 형태를 따로 갖는다**(Figma `186:6839` 미저장 경고 · `190:9039` 메모 삭제). 위 모달보다 넓고 낮으며, 스크롤도 구분선도 없이 한 덩어리다. 버튼 배치가 경고마다 다르므로(3버튼 경고는 좌우로 갈라지고, 삭제 확인은 우측으로 몰린다) 셸은 상자만 잡고 안쪽은 내용에 맡긴다.

- **alert은 스크림 탭으로 닫지 않는다.** 되돌릴 수 없는 조작이거나 데이터가 걸린 갈림길이라 선택지 중 하나를 명시적으로 골라야 한다. 뒤로가기는 열려 있다(3.5절)
- 갈라지는 것은 상자 모양뿐이고 **history 처리는 모달과 같은 한 벌을 공유한다.** 경고마다 다시 짜면 뒤로가기 동작이 한쪽만 틀어진다

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 모달을 부모 쪽에서 곧바로 걷으면, 셸이 올려둔 history 엔트리가 남는다 |
| 위반 원칙 | Safety and Trust — 남은 엔트리가 다음 뒤로가기 제스처를 소리 없이 삼켜, 사용자는 뒤로가기가 고장 난 것으로 읽는다 |
| 변경 전 | 버튼이 결과를 바로 부모에게 올리고 부모가 모달을 제거 |
| 변경 후 | **어느 버튼이든 셸의 dismiss를 거쳐 닫는다.** 선택만 기억해 두었다가 엔트리가 사라진 뒤 부모에게 올린다 |
| 검증 상태 | 내부 검토 (브라우저에서 주소 쿼리 잔여 없음을 확인) |

> **확인 필요:** 확인 모달과 드래그 고스트는 Figma 화면이 없는 초안이다.

#### 4.0.5. 우측 환자 패널의 조작

패널은 `최근 환자`(앞 3명)와 `전체 환자` 두 구간으로 나뉜다. 환자 행의 탭·꾹 누르기는 4.0.2절 문법을 그대로 따르고, 이 절은 구간 머리의 조작을 다룬다.

**전체 환자 머리는 전체 환자 리스트로 가는 진입점이다.**

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 구간 머리에 chevron이 붙어 '더 있다'고 말하는데 눌러도 아무 일이 없었다 |
| 위반 원칙 | Safety and Trust — 반응 없는 조작은 고장으로 읽힌다(3.8절) |
| 변경 후 | **머리(라벨 + chevron)를 누르면 전체 환자 리스트로 간다.** 탭은 탐색이고 상태를 바꾸지 않으므로(3.5절) 버튼 하나가 아니라 라벨과 chevron을 묶은 행 전체가 대상이다. 정렬 버튼만 따로 떼어 둔다 |
| 거부된 대안 | chevron만 누르게 함 — 터치 타깃이 16px로 최소 44 규정에 미달한다. / chevron 제거 — 리스트로 가는 진입점이 하나 줄어든다(4.5절 기준 넷 중 하나) |
| 검증 상태 | 내부 검토 (DOM 확인) |

**정렬 기준은 전체 환자 리스트 화면과 같다.**

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 같은 명단을 패널과 리스트 화면 두 자리에서 보는데, 패널은 목업 배열 순서로 나열되어 기준을 짐작할 수 없었다 |
| 위반 원칙 | Consistency — 같은 '전체 환자'가 자리마다 다른 순서를 갖는다 |
| 변경 후 | `가나다순`(기본) / `최근 진료순` / `진단순` 셋이다. 앞의 둘은 **4.4절 리스트 화면과 같은 기준**이고, 진료 기록이 없는 사람은 최근 진료순에서 뒤로 보낸다 — 최근이라 할 것이 없다. **진단순의 나열 순서는 분석 화면의 진단 축과 같은 배열에서 온다**(4.3절) — 순서를 여기 다시 적으면 차트의 막대 순서와 갈라진다. 같은 진단 안에서는 가나다순이다. 컨트롤은 4.1.3절과 같은 팝오버이고, 열려 있는 동안 아이콘이 accent다(선택 상태) |
| 거부된 대안 | 패널 전용 기준(예: 최근 조회순) — 두 자리의 순서가 갈린다. / 아이콘 토글 — 현재 기준을 알 수 없다(4.1.3절과 같은 이유) |
| 검증 상태 | 내부 검토 (DOM 확인) |

- **명단 원본을 정렬하지 않는다.** `최근 환자` 구간이 명단 앞 3명을 참조하므로, 원본을 정렬하면 그 구간까지 같이 바뀐다. 패널은 정렬된 사본을 그린다.
- 팝오버는 패널 밖으로 내보낸다. 패널이 세로 스크롤 상자라 안에 두면 잘린다.
- 정렬에는 `진단순`과 `단계순`이 더 있다. 두 축의 나열 순서는 모두 4.3절의 축 정의에서 가져온다 — 순서를 화면에 다시 적으면 차트의 막대 순서·프로세스의 단계 순서와 갈라진다.
- **검색은 이름·진단에 더해 현재 단계도 본다.** `감정평가`를 치면 그 단계의 환자만 남는다. 패널에는 필터를 둘 자리가 없어(폭 274) 검색이 그 일을 겸한다. 같은 축이 전체 환자 리스트에는 필터로 올라가 있다(4.4절).

**검색은 패널 안에서 거른다.**

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 패널 상단의 검색 입구가 눌러도 아무 일이 없었다 |
| 위반 원칙 | Safety and Trust (3.8절) |
| 변경 후 | **패널 안에서 거르고, 검색 중에는 두 구간을 합쳐 `검색 결과` 하나로 보여준다.** 이름과 진단이 대상이며, 정렬 기준은 그대로 적용된다. 결과가 없으면 그렇다고 말한다 |
| 거부된 대안 | 전체 환자 리스트 화면으로 이동 — **검색 결과를 꾹 눌러 일정에 배치하는 길이 끊긴다.** 패널의 존재 이유는 어느 화면에서 일하든 환자를 그 자리에서 집어 오는 것이다(4.0.3절). 리스트 화면으로 가면 그 화면은 패널을 쓰지 않으므로 작업 맥락도 함께 사라진다 |
| 검증 상태 | 내부 검토 (DOM 확인) |

배치 모달의 환자 리스트가 같은 문법을 쓴다(4.0.4절) — 그쪽이 패널 구조를 옮겨 온 것이므로 검색 동작도 같아야 한다. 행 마크업은 세 구간이 한 벌을 공유한다. 구간마다 복제하면 한쪽만 고쳐진다.

> **확인 필요:** 패널의 정렬 팝오버와 `단계순`·`진단순` 기준은 Figma에 근거가 없는 초안이다. 리스트 화면의 것과 같은 모양으로 두었다. 6.2절 14번 항목 참조.

#### 4.0.6. 좌측 네비의 알림 · 설정 · 프로필

> **확인 필요:** 세 자리 모두 **Figma 디자인이 없어 임의로 만든 것이다.** 디자인이 나오면 교체한다. 6.2절 34번 항목 참조.

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 좌측 네비 하단의 `알림`·`설정`이 눌러도 아무 일이 없었다. 프로필 사진은 로고 원본을 그대로 넣어 워드마크까지 36px 원 안에 들어가 글자가 뭉개졌다 |
| 위반 원칙 | Safety and Trust (3.8절 — 반응이 없으면 고장으로 읽힌다) |
| 변경 후 | **알림은 팝오버, 설정은 모달**이다. 프로필은 심볼만 정사각으로 잘라 원을 채운다 |
| 검증 상태 | 내부 검토 (DOM 확인) |

**알림이 팝오버인 이유**는 읽고 지나가는 가벼운 콘텐츠이기 때문이다(3.5절). history 엔트리를 만들지 않고 외부 탭으로 닫는다. 폭 280 · 최대 높이 364는 캘린더 날짜 팝오버와 같은 값이다 — 같은 문법의 자리를 두 크기로 두지 않는다. 좌측 네비가 화면 왼쪽 끝이라 **버튼의 오른쪽에** 붙이고 세로는 버튼 중앙에 맞추되 화면 밖으로 나가지 않게 가둔다.

- **읽지 않음에 accent를 쓰지 않는다.** accent 용법은 셋으로 동결돼 있다(3.1절). 읽지 않은 항목은 표면(`surface-field`)과 글자 굵기로 가르고, 버튼의 개수 배지는 중립 채움이다
- 항목을 탭하면 읽음으로 바꾸고 관련 화면으로 간다. 팝오버를 먼저 닫아 이동이 한 번에 끝나게 한다
- 기한이 지난 작업만 경고색이다 — 악화 표현 전용 규칙(3.1절)
- 빈 상태를 둔다. 아무것도 없는 상자만 남으면 고장으로 읽힌다

**설정이 모달인 이유**는 값을 바꾸고 저장하는 자리이기 때문이다. **사본을 고치고 `저장`에서 한 번에 반영한다** — 스위치를 누를 때마다 반영하면 `취소`가 되돌릴 것이 없다(3.6절 오토세이브 없음).

| 필드 | 내용 |
| --- | --- |
| 거부된 대안 | ① 설정도 팝오버 — 저장·취소가 있는 자리라 외부 탭으로 사라지면 고르던 값이 소리 없이 버려진다. ② 스위치 즉시 반영 — 오토세이브 없음 규칙과 어긋난다. ③ 설정 안에 테마 토글 — **좌측 하단에 이미 있다.** 같은 조작을 두 자리에 두면 어느 쪽이 지금 값인지 알 수 없고 한쪽만 고치면 갈라진다 |

스위치의 켠 상태는 **채운 표면**(`surface-inverse`)이다. accent를 쓰지 않는 이유는 위와 같다.

**프로필 사진은 심볼만 남긴 정사각을 쓴다.** 원본 로고는 심볼 아래에 워드마크가 붙은 가로형이라 36px 원에 통째로 넣으면 글자가 뭉개지고 위아래에 빈 띠가 남는다. 심볼의 잉크 경계를 재서 잘라내고 정사각 캔버스 가운데에 얹은 파일을 `object-cover`로 채운다. 원본은 다른 이름으로 남겨 뒀다.

#### 4.0.7. 로그인과 역할 분기

> **확인 필요:** 로그인 화면과 환자용 첫 화면은 **Figma 디자인이 없어 임의로 만든 것이다.** 6.2절 35번 항목 참조.

앱의 첫 화면이다. 셸을 걷는다(`meta.bare`) — 아직 누구인지 정해지지 않아 좌측 네비를 그릴 수 없고, **로그인 전에 우측 패널의 환자 명단이 보이면 안 된다.**

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 앱을 열면 곧바로 상담사 화면이 나와, 누가 쓰는 기기인지와 무관하게 환자 명단이 보였다 |
| 위반 원칙 | Safety and Trust (1.2절 — 타 환자 정보 노출) |
| 변경 후 | **역할을 먼저 고르고 그 다음에 입력한다.** 치유사는 아이디·소속 코드, 환자는 이름·생년월일을 묻는다. 역할을 바꾸면 입력 칸의 뜻이 달라지므로 앞서 친 값을 비운다 |
| 거부된 대안 | 한 폼에 다 넣고 역할을 나중에 고르기 — 방금 채운 칸이 쓸모없어지는 경우가 생긴다 |
| 검증 상태 | 내부 검토 (DOM 확인) |

- **인증을 흉내 내지 않는다.** 백엔드가 없어 무엇을 넣어도 통과하며, 화면에도 그렇게 적어 둔다 — 막히는 것처럼 보이면 고장으로 읽힌다. 첫 칸이 비어 있을 때만 사유 콜아웃을 띄운다
- **가드는 라우터 한 곳이다.** 화면마다 검사하면 한 곳만 빠져도 우회로가 된다. 세션이 없으면 어느 화면도 열리지 않고, **환자 세션으로는 상담사 화면이 열리지 않는다** — 설문 수행만 예외다(상담사가 건네준 화면이라 환자가 조작하는 것이 맞다)
- **세션은 `sessionStorage`에 남긴다.** 새로고침으로 로그아웃되면 안 되지만, 탭을 닫으면 지워져야 한다 — 병원에서 함께 쓰는 기기라 앱을 닫았다 열면 다시 물어야 한다. `localStorage`였다면 다음 사람이 앞사람 계정으로 들어간다
**환자는 계정을 만들지 않고 1회용 접속 코드로 들어온다.**

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 환자를 무엇으로 식별할 것인가 |
| 위반 원칙 | Safety and Trust (1.2절) |
| 변경 전 | 이름과 생년월일을 물었다 |
| 변경 후 | **상담사가 그 자리에서 발급한 코드**(숫자 6자리)만 통한다. 코드가 곧 신원이므로 환자 쪽만 값을 검사한다 — 아무 코드나 통과시키면 누구의 기록을 열지 정해지지 않는다 |
| 거부된 대안 | 이름 + 생년월일 — 태블릿을 건네받는 자리라 계정을 만들 이유가 없고, **아는 사람의 정보로 남의 기록을 열 수 있다** |
| 검증 상태 | 사용자 결정(2026-08-19) · DOM 확인 |

**코드는 환자 상세에서 발급한다.** 환자가 자기 화면에 들어오는 유일한 길이므로 발급 자리가 환자를 다루는 화면 안에 있어야 한다. 짧은 확인이라 alert 상자를 쓴다.

- **새로 발급하면 이전 코드는 무효**가 된다. 둘 다 살아 있으면 회수하지 못한 종이 한 장이 계속 열쇠로 남는다
- 새로 냈다는 사실을 경고색으로 남긴다 — 앞서 알려준 코드가 방금 막혔기 때문이다
- 열 때마다 새로 내지 않는다. 살아 있는 코드가 있으면 그것을 보여준다

> **확인 필요:** 코드의 발급·소멸은 백엔드의 일이다. 프로토타입에서는 **한 번 쓴 코드가 소진되지 않으며**, 로그인 화면이 그 사실과 시연용 코드를 그대로 밝힌다.

#### 4.0.8. 환자용 첫 화면

> **확인 필요:** **Figma 디자인이 없어 임의로 만든 것이다.** 구버전 웹 화면의 구성(변화 그래프 · 설문 할 일 · 치유 기록)만 참고했다. 6.2절 35번 항목 참조.

세 칸이다 — 위 왼쪽 **마음의 변화**, 위 오른쪽 **작성할 설문**, 아래 **치유 기록**.

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 환자가 자기 화면에서 무엇을 보고 무엇을 할 수 있어야 하는가 |
| 변경 후 | **할 일이 제일 크다.** 이 화면에 온 이유가 대개 설문 작성이므로 오른쪽 위에 고정하고, 미완료를 위로 정렬한다. 나머지 둘은 '어디까지 왔는지'다 |
| 값의 출처 | 전부 상담사 화면과 **같은 원본**이다 — 설문은 `surveys.js`, 변화는 `keyMetricsOf`, 회차는 수행 기록, 기록은 프로세스 이력. 환자용 목업을 따로 두면 상담 자리에서 두 화면이 어긋난다 |
| 검증 상태 | 내부 검토 (DOM 확인) |

- **셸이 없다.** 좌측 네비로 다른 환자에게 갈 길이 있으면 안 된다(4.0.1절의 네 번째 갈래와 같은 이유)
- **판정·진단 용어를 앞세우지 않는다.** 점수와 등급은 상담사가 설명할 몫이다. 그래프도 **개선·악화로 판정하지 않고** 얼마나 달라졌는지만 적는다 — 지표마다 좋아지는 방향이 다르다(회복탄력성은 높을수록, 우울은 낮을수록)
- **지표에는 이름이 둘이다.** 상담사는 임상 용어(`우울 · 불안` · `강박성`)를, 환자는 순화한 이름(`마음의 무게` · `반복되는 생각`)을 본다. 임상 용어를 그대로 내밀면 자기 화면이 진단서가 된다. 두 이름은 한 배열에 나란히 둔다 — 두 곳에 적으면 짝이 어긋난다
- **치유 기록은 프로그램 단위다.** 환자가 참여한 것은 프로그램이고, 프로세스 이름과 버전(`PTSD_v1.0`)은 우리 쪽 관리 단위라 환자 화면에 내밀지 않는다. ⚠️ 지난 프로그램이 무엇이었는지는 목업에 없어(이력에 버전만 있다) 진단에 맞는 프로그램 중에서 결정론적으로 고른다
- **환자 세션에서는 제출 뒤 완료 알림 화면을 거치지 않는다.** 그 화면의 목적은 태블릿이 아직 환자 손에 있을 때 상담사용으로 곧장 돌아가지 않게 막는 것이다. 환자가 자기 화면에서 열었다면 돌아갈 곳이 자기 화면이라 막을 것이 없고, '태블릿을 전달해 주세요'도 맞지 않는 말이 된다. **상담사가 건네준 경우에만** 알림 화면이 남는다
- **끝낸 설문은 다시 열리지 않는다.** 되돌리는 것은 상담사가 할 일이다(4.6.2절의 잠금 규칙과 같은 자리)
- **회차를 아직 지나지 않았으면 그래프 자리에 다음 만남을 둔다.** 그릴 선이 없다고 빈칸으로 두지 않고, 지어낸 값도 쓰지 않는다 — 일정에서 읽는다
- 설문 수행 화면의 복귀 버튼은 **누가 들고 있느냐**를 따른다. 환자 세션이면 `내 화면으로 돌아가기`이고 자기 화면으로 간다 — 상담사 화면으로 보내면 가드가 되돌려 화면이 한 번 튄다
- **환자용 첫 화면은 할 수 있는 일을 지어내지 않는다.** 명단에 없는 코드로 들어온 경우처럼 보여줄 것이 없으면 그렇다고 말하고 나가는 길을 둔다. 나가는 버튼은 안내 카드 **밖에** 떨어뜨린다 — 안에 붙이면 '확인' 버튼으로 읽힌다(설문 완료 알림 화면과 같은 결정)
- **로그아웃은 설정 모달 안에 있고 확인을 거친다.** 되돌릴 수 없고 고르던 설정도 함께 버려진다. 중복 경고와 같은 문법으로 버튼 행만 확인 상태로 바뀐다(4.0.6절)

### 4.1. 홈 (업무)

빠른 저작 · 작업 목록 · 일정 타임라인(아젠다)으로 구성된다. 빠른 저작은 저작도구의 즐겨찾기를 펴는 자리다(4.8.11절).

#### 4.1.1. 작업 모델의 통합

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | '미배정 할 일'과 '일정에 놓인 업무'를 별개 개념으로 두면, 배치할 때 목록에서 사라져 리마인더 기능을 잃고, 완료 상태가 두 곳에 생긴다 |
| 위반 원칙 | Consistency, Safety and Trust (상태 불일치) |
| 변경 전 | 할 일 목록과 일정 업무를 별도 데이터로 관리 |
| 변경 후 | **하나의 '작업'이 날짜·시간을 갖거나 갖지 않을 뿐이다.** 명칭도 '작업'으로 통일. 배치해도 목록에서 사라지지 않으며, 목록에서 내려가는 유일한 길은 **완료**다. 타임라인의 업무 블록은 작업에서 파생된다(3.7절) |
| 거부된 대안 | 배치 시 목록에서 제거 — 리마인더 기능 상실. / 양쪽에 각각 완료 상태 — 불일치 발생 |
| 검증 상태 | 내부 검토 |

- 완료는 명시적 조작이고 되돌리기도 같은 자리(작업 상세)에서 한다.
- **삭제도 같은 자리에 둔다.** 완료와 삭제는 다른 일이다 — 완료는 '했다'는 기록이라 완료 구간에 남지만, 삭제는 애초에 없었던 것으로 만든다(잘못 만든 작업을 치우는 길). 삭제는 되돌릴 수 없으므로 3.6절의 삭제 확인을 거치며, 버튼은 테두리만 둔 형태로 왼쪽에 떨어뜨린다 — 파괴적인 것을 강조하지 않는다. 일정 상세의 삭제와 같은 배치·같은 문구 구조다.
- 배치된 작업을 삭제하면 **타임라인의 업무 블록도 함께 사라진다.** 블록이 작업에서 파생되기 때문이고(4.1.1절), 이것이 두 모델을 하나로 둔 이득이다.
- 작업 목록은 아코디언 3구간(`미배정` → `배정됨` → `완료`)이며 **완료만 기본으로 접혀 있다.** 배정 여부는 시간의 유무가 정한다 — 날짜만 있고 시간이 없으면 타임라인에 자리가 없으므로 미배정이다.
- 헤더의 개수는 **미완료 총합**이다.
- 완료된 작업은 배치 대상이 아니다. 꾹 누르기가 걸리지 않고 탭만 받는다.

#### 4.1.2. 작업 행의 시점 라벨

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 좁은 폭에 날짜를 표시해야 하는데, 축약 표기는 읽는 데 재계산이 필요하다 |
| 위반 원칙 | Minimalism vs Experience — 자리 절약과 즉시 판독의 충돌 |
| 변경 후 | 어제·오늘·내일만 상대 표기로 줄이고 나머지는 날짜 표기. 시간이 있으면 뒤에 붙인다. 기한이 지난 **미완료** 작업만 `N일 지남` + 경고색 |
| 거부된 대안 | `D-3` 형태 — 자리는 아끼지만 날짜를 다시 계산해야 읽히고, 지난 건이 `D+1`이 되어 부호가 헷갈린다 |
| 검증 상태 | 내부 검토 |

#### 4.1.3. 정렬 기준의 표현

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 작업 목록 헤더의 가용 폭이 좁아 정렬 컨트롤에 약 44px만 배정 가능하다 |
| 위반 원칙 | Efficiency vs Consistency |
| 변경 후 | 아이콘 버튼을 누르면 기준을 고르는 **팝오버**가 열린다. 기준은 `시간 빠른 순`(기본) / `추가한 순` 두 가지이며, 시간 빠른 순은 날짜 다음에 시각까지 본다. 날짜 미정은 맨 뒤로 간다 |
| 거부된 대안 | 아이콘 토글 — 아이콘만으로는 현재 어떤 기준이 걸려 있는지 알 수 없다 |
| 검증 상태 | 내부 검토 |

#### 4.1.4. 지난 시간 행의 표현

2.1.2절 사례 B 참조. opacity 대신 배경 토큰을 교체한다.

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 지금 시각의 경계를 드러내야 하지만, 지난 행의 정보도 여전히 읽혀야 한다 |
| 위반 원칙 | Safety and Trust (판독 가능성) |
| 변경 전 | `opacity`로 행 전체를 낮춤 — 실측 제목 4.44 · 메타 2.99로 대비 기준 미달 |
| 변경 후 | 배경 토큰만 반 단계 아래로 교체(3.4절 표면 계단). 글자는 온전한 토큰 대비를 유지 — 실측 제목 7.21 · 메타 7.21 · 시간 7.75. 제목은 secondary로 낮춘다 |
| 거부된 대안 | `opacity-80` — 4.68까지밖에 오르지 않아 여전히 미달 |
| 검증 상태 | 내부 검토 (명도 대비 실측 완료) |

드래그 중에는 이 배경을 적용하지 않는다. 드롭 불가 표현과 겹친다.

**진행 중은 명도가 아니라 accent 배지로 표시한다.** 명도로 표현하면 지난/현재/예정이 모두 명도 축에 올라 구분이 무뎌진다.

#### 4.1.5. 타임라인의 선택 상태

**타임라인에는 선택 상태를 두지 않는다.** accent는 '진행 중' 배지와 드롭 대상에만 쓴다.

**단 하나의 예외** — 한 시간에 작업이 여러 건 들어갈 수 있어(환자 일정은 한 건뿐) 행에는 대표 한 건만 보이고 나머지는 접힌다. 접힌 행을 누르면 그 시간의 목록이 팝오버로 열리는데, **팝오버가 열려 있는 동안 그 행은 선택 상태다.** 목록을 보는 동안 어느 행에서 열렸는지 잃지 않기 위함이며, 3.1절 accent 용법 '선택 상태'에 해당한다.

대표는 **완료되지 않은 것 우선, 그 안에서 마지막으로 추가된 것**이다. 팝오버는 가벼운 콘텐츠이므로 모달이 아니며 history 엔트리를 만들지 않는다(3.5절). 손에 의한 가림을 피해 행 왼쪽에 붙인다(2.3.1절).

#### 4.1.6. 배치 유형과 단계 표시

배치 유형은 `일반 상담` / `치유 프로세스` 둘 중 하나다.

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 치유 프로세스로 배치할 때 어느 단계를 하는 자리인지 모달에 표시할 것인가 |
| 위반 원칙 | Minimalism |
| 변경 전 | 유형을 '치유 프로세스'로 고르면 그 아래에 `다음 단계 · 감정평가`처럼 환자의 다음 단계를 읽어 보여주었다. 다음 단계가 없는 환자(완료·중단)는 치유 프로세스로 배치할 수 없었다 |
| 변경 후 | **모달에서 단계를 고르지도 표시하지도 않는다.** 유형 둘만 고른다. 다음 단계 유무로 배치를 막지 않는다 |
| 근거 | 상담사와 환자가 **대면하는 순간은 감정평가 · 프로그램 수행 · 일반 상담 셋뿐**이다. 프로세스 개시(프로세스 할당) · 프로그램 처방(프로그램 선택) · 프로세스 종료는 상담사가 혼자 처리하는 단계라 약속을 잡을 대상이 아니다. 따라서 '치유 프로세스'로 잡은 자리에서 무엇을 하는지는 프로세스가 이미 정하고 있어, 단계를 한 줄 더 적어도 새로 알려주는 것이 없다 |
| 거부된 대안 | ① 상담사가 단계를 직접 선택 — 환자마다 단계 구성과 횟수가 달라 앱이 계산할 수 없고(실제로는 백엔드가 내려줄 값), 아직 도달하지 않은 단계에 임의로 접근하면 시스템 안정성이 깨진다. ② 다음 단계를 읽어 표시(변경 전) — 위 근거대로 정보가 늘지 않는데, 다음 단계가 없다는 이유로 완료·중단 환자를 치유 프로세스로 잡지 못하게 막는 부작용까지 따라왔다 |
| 검증 상태 | 사용자 피드백 반영(2026-08-19) · 내부 검토 |

유형의 **기본값은 환자의 프로세스 상태가 정한다** — 프로세스가 `완료`·`중단`이면 `일반 상담`, 그 밖에는 `치유 프로세스`다. 프로세스가 끝났거나 끊긴 환자를 만나는 일은 프로세스 안의 일이 아니다.

> **확인 필요:** 대면하는 순간이 셋뿐이라면 유형을 `감정평가` / `프로그램 수행` / `일반 상담` 셋으로 두는 안도 성립한다. 지금은 유형 둘을 유지했다.

**일정 블록에는 그 자리에서 무엇을 하는지가 남는다** — `진단 · 감정평가 (사후)` · `진단 · 프로그램 수행 (6/10)` · `진단 · 일반 상담`. 나오는 값은 대면하는 순간 셋뿐이다.

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 모달에서 단계를 걷어내면 일정 블록에도 유형만 남아, 타임라인이 온통 `치유 프로세스`가 된다. Figma 홈 화면의 블록은 `프로그램 수행 (5/8)`이었다 |
| 위반 원칙 | Safety and Trust — 오늘 몇 회차를 하는 자리인지 모른 채 환자를 맞게 된다 |
| 변경 후 | **프로그램 수행은 몇 회차인지까지 적는다.** 값은 **배치하는 순간의 진행 지점을 일정에 적어둔 것**이고(`visitDetail`), 그리는 시점에 환자에서 읽지 않는다 — 그러면 지난 일정의 회차까지 오늘 값으로 바뀐다. 3.x절 '일정은 환자의 현재 상태를 참조하지 않는다'를 지키는 자리다 |
| 아직 정해지지 않은 경우 | 프로세스 시작 · 프로그램 처방 · 프로세스 종료 단계의 환자를 치유 프로세스로 잡으면 대면 내용이 아직 없으므로 유형 이름(`치유 프로세스`)이 그대로 남는다 |
| 거부된 대안 | 그릴 때 환자 상태에서 읽어 붙이기 — 지난 일정이 오늘의 회차로 바뀐다. 같은 회차를 두 화면이 다르게 말하는 것과 같은 결함이다 |
| 검증 상태 | 사용자 피드백 반영(2026-08-19) · DOM 확인 |

**단계를 걷어낸 자리에는 '지금 어디까지 왔는가'가 들어간다.** 앞으로 무엇을 할지는 프로세스가 정하지만, 지금 어디에 있는지는 상담사가 약속을 잡기 전에 알아야 한다.

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 단계 표시를 걷어내면 배치 모달에 환자의 상태가 전혀 남지 않는다. 프로세스가 없는 환자에게 치유 프로세스 일정을 잡거나, 절반만 끝낸 감정평가를 처음부터 다시 하는 것으로 오해할 수 있다 |
| 위반 원칙 | Safety and Trust (2.1절 최상위) |
| 변경 후 | 대상이 환자면 **`현재 진행` 한 줄**을 낸다. 현재 단계와 함께 **몇 개 중 몇 개인지**까지 적는다 — 감정평가는 `설문 7개 중 4개 작성`, 프로그램 수행은 `6회차 중 3회차 진행 중`이다. 단계 이름만으로는 하나도 손대지 않은 것과 거의 끝낸 것이 같아 보인다 |
| 경고색을 쓰는 두 경우 | **프로세스 미배정**(시작 전)과 **프로세스 중단**. 둘 다 약속을 잡기 전에 알아야 하는 상태다. 완료는 악화가 아니므로 중립색이다(3.1절) |
| 거부된 대안 | 진행 상황을 환자 레코드에 문자열로 적어둠 — 설문 응답·회차 기록이 바뀔 때마다 갱신해야 하고, 한쪽만 갱신되면 갈라진다. 값은 전부 원본(`surveys.js`·`sessions.js`)에서 읽는다 |
| 검증 상태 | 사용자 피드백 반영(2026-08-19) · DOM 확인 |

**프로세스가 배정되지 않은 환자를 치유 프로세스로 잡으려 하면 배정하러 보낸다.**

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 프로세스가 없는 환자에게 치유 프로세스 일정을 잡으려 할 때 무엇을 할 것인가 |
| 위반 원칙 | Safety and Trust |
| 변경 후 | 확인을 거쳐 **프로세스 개시(0단계) 화면으로 보낸다.** 프로세스가 붙어야 감정평가든 프로그램 수행이든 그 자리에서 할 일이 정해진다 — 그대로 배치하면 무엇을 하는 자리인지 정해지지 않은 일정이 남는다. 잡던 일정은 배정을 마친 뒤 다시 잡는다 |
| 문법 | 중복 경고와 같다: **모달을 닫지 않고 버튼 행만 확인 상태로 바뀌며, `돌아가기`는 고르던 자리로 되돌린다.** 유형을 `일반 상담`으로 바꾸면 그대로 배치할 수 있다 |
| 거부된 대안 | 경고만 하고 그대로 배치 — 내용이 비어 있는 일정이 남고, 배정을 잊으면 그 자리에서 할 것이 없다 |
| 이동 시점 | 모달이 닫힌 **뒤에** 이동한다. 셸이 올려둔 history 엔트리를 라우터가 걷어내기 전에 이동하면 모달 엔트리가 스택에 남는다(3.5절) |
| 검증 상태 | 사용자 피드백 반영(2026-08-19) · DOM 확인 |

#### 4.1.7. 업무의 날짜·시간 미정 허용

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 작업 추가 시점에 날짜·시간이 정해지지 않은 경우가 있다 |
| 변경 후 | **업무는 날짜·시간을 '미정'으로 둘 수 있다. 환자 일정은 둘 수 없다** — 환자를 만나는 일에는 반드시 날짜와 시간이 있다. `미정` 칩을 선택지 맨 앞에 두고 대상이 '업무'일 때만 렌더한다. 날짜가 미정이면 고를 시간 자체가 없으므로 시간 구간을 숨긴다 |
| 거부된 대안 | 환자 일정도 미정 허용 — 시간 없는 일정은 타임라인에 그릴 자리가 없고, 만날 약속으로서도 성립하지 않는다 |
| 검증 상태 | 내부 검토 |

날짜가 이미 정해진 경로(아젠다·팝오버)에서도 **업무일 때는 날짜 구간을 계속 보여준다.** 미정으로 되돌릴 길이 없으면 안 되기 때문이다.

### 4.2. 일정 (캘린더)

6주 × 7일 42칸 고정 월 그리드. 주 시작은 월요일.

#### 4.2.1. 격자의 표현

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 42칸에 각각 border를 그리면 인접 변이 겹쳐 선 굵기가 불균일해지고, 라운드를 주면 모서리에서 배경이 비친다 |
| 위반 원칙 | Experience, Consistency |
| 변경 후 | **요일 머리부터 격자까지 한 판을 구분선 색으로 채우고, 날짜 칸만 표면색으로 덮는다.** 칸 사이 1px 간격과 요일 머리 행에서 판이 그대로 보인다. 셀에는 border도 라운드도 주지 않는다 |
| 거부된 대안 | 셀별 border — 겹침으로 굵기 불균일. / 셀 라운드 — 모서리에서 판이 비쳐 외곽선처럼 보인다 |
| 검증 상태 | 내부 검토 |

요일 머리는 opacity 없이 secondary 색을 쓴다. 구분선 배경 위에서 opacity를 씌우면 글자가 배경에 씻겨 읽히지 않는다.

선택된 칸은 선택 배경 + **inset ring**으로 표시한다. border로 주면 자리를 차지해 선택 순간 텍스트가 밀린다.

#### 4.2.2. 앞뒤 달 칸의 처리

앞뒤 달 칸은 배경을 바꾸지 않고 칸 전체에 opacity를 주며 글자만 secondary로 낮춘다. **단 드래그 중에는 이 opacity를 걷어낸다** — 드롭 배경까지 함께 씻겨 어디가 대상인지 보이지 않기 때문이다. 같은 이유로 **누르는 동안에도 걷어낸다**(3.8절).

#### 4.2.3. 칸 탭의 결과

| 칸의 상태 | 탭의 결과 |
| --- | --- |
| 일정이 있음 | 그날 목록 팝오버 (폭 280 / 최대 높이 364). 환자 일정에만 우측 chevron으로 상세 진입 |
| 일정이 없음 | 그 날짜로 '일정 추가' 모달 |
| 지난 날 | 아무 일도 하지 않는다 (배치할 수 없는 날이므로 추가할 것도 없다) |

셀당 일정은 두 건까지만 보이고 나머지는 접힌다 — 아젠다의 `+N` 문법과 동일하다(Consistency).

팝오버는 칸 오른쪽에 붙이고 세로는 칸 중앙에 맞추되 화면 밖으로 나가지 않게 가둔다(2.3.1절 손에 의한 가림).

### 4.3. 환자 분석

KPI 카드 → 필터 칩 행 → 프로세스 상태·진단 유형 2열 → 연령대·성별 2열.

#### 4.3.1. 집계의 출처와 상호 관계

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 각 차트가 어떤 모집단을 세는지가 불명확하면, 강조된 구간의 합과 KPI 값이 어긋난다 |
| 위반 원칙 | Safety and Trust (수치 신뢰성) |
| 변경 후 | 집계는 화면이 환자 명단에서 직접 센다(3.7절). **각 차트는 자기 축을 뺀 나머지 필터를 적용한 분포를 센다.** 그 결과 **강조된 구간의 합이 언제나 KPI와 같다** |
| 거부된 대안 | 별도 집계 목업 — 명단과 갈라진다. / 모든 필터를 각 차트에 적용 — 자기 축이 항상 단일 구간으로 붕괴되어 분포를 볼 수 없다 |
| 검증 상태 | 내부 검토 (Figma 원안에서 강조 구간이 모두 동일 인원으로 떨어지는 관계와 일치) |

#### 4.3.2. 막대의 상호작용과 길이 규칙

- **차트의 accent는 '선택 상태'다**(3.1절 용법 내).
- **막대를 누르면 그 구간이 필터에 들고 난다.** 히트 영역은 행/칸 전체이며 트랙의 빈 부분까지 포함한다(3.3절).
- **성별은 칩(원)과 막대 둘 다 같은 필터를 건다.** 막대는 좌우가 각각 자기 성별이다. 한쪽이 0명이면 그 구간의 폭도 0이 되지만 원이 남아 있어 조작 경로가 막히지 않는다.
- **칩은 축 단위다.** 탭하면 그 축이 통째로 풀린다. 라벨은 고른 순서가 아니라 축의 구간 순서를 따른다.
- **막대 길이 = 값 / 최대값 × 트랙의 90%, 최소 8%.** 다만 **0명은 최소 길이도 주지 않는다** — 없는 것을 있는 것처럼 그리면 안 된다(Safety and Trust).
- 성별만 분포가 아니라 **비율**이다. 둘이 합쳐 트랙을 채운다.

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 두 카드의 라벨 폭이 달라(50 vs 60), 트랙을 유연 폭으로 두면 카드마다 트랙 길이가 갈라진다 |
| 위반 원칙 | Consistency — 카드 사이의 막대를 비교할 수 없게 된다 |
| 변경 후 | **가로 막대 트랙은 두 카드에서 같은 폭으로 고정한다** |
| 검증 상태 | 내부 검토 |

> **확인 필요:** 현재 환자 명단은 임의 표본이라 Figma의 인원 규모와 다르다. 실제 값이 확정되면 명단을 교체한다.

### 4.4. 전체 환자 리스트

검색 섹션(검색바 · 필터 · 정렬 · 칩 행 · 건수) + 리스트 카드(헤더 + 행). 우측 환자 패널을 쓰지 않는다(4.0.1절).

#### 4.4.1. KPI에서 넘어오는 필터

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 분석 화면에서 필터가 걸린 상태의 KPI를 눌렀는데 리스트가 전체를 보여주면, '5명'을 눌렀는데 40명이 나온다 |
| 위반 원칙 | Safety and Trust (수치 신뢰성), Consistency |
| 변경 후 | **KPI를 누르면 그때 걸린 칩이 쿼리로 넘어온다.** 리스트에서 필터를 바꾸면 주소도 따라가므로 새로고침·뒤로가기가 같은 결과를 낸다 |
| 거부된 대안 | 전역 상태로 필터 전달 — 주소와 화면이 갈라져 뒤로가기 결과가 달라진다 |
| 검증 상태 | 내부 검토 |

#### 4.4.2. 표의 열 폭

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | Figma에서 헤더와 행의 열 폭이 서로 다르게 지정되어 있어, 그대로 옮기면 표가 어긋난다 |
| 위반 원칙 | Consistency |
| 변경 후 | **헤더와 행이 같은 열 폭·간격을 쓴다.** 행 쪽 값에 맞췄다 |
| 검증 상태 | 내부 검토 (Figma와의 차이를 의도적으로 둔 항목) |

#### 4.4.3. 파생 열의 표기

- **마지막 진료 · 다음 일정은 일정에서 뽑는다**(3.7절). 업무 블록은 진료가 아니므로 환자 일정만 본다.
- 마지막 진료는 `오늘` / `어제` / `N일 전`. 오늘 지나간 진료가 `0일 전`으로 읽히면 안 된다.
- **다음 일정이 없으면 경고색 + dot.** 잡아야 할 것이 남았다는 뜻이므로 악화 표현에 해당한다(3.1절).

#### 4.4.5. 필터 축과 축의 경계

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 팝오버가 축(프로세스 상태 · 진단 유형 · 연령대 · 성별)을 이어 붙이는데 축 이름이 항목과 같은 표면에 있어, 어디까지가 한 축인지 읽히지 않았다 |
| 위반 원칙 | Consistency, Experience |
| 변경 후 | **축 머리를 필드 표면으로 깔고 위아래에 구분선을 둔다.** 항목 행은 카드 표면이라 머리와 갈린다 |
| 거부된 대안 | 축마다 별도 팝오버 — 여러 축을 동시에 거는 일이 잦아 여닫는 횟수가 늘어난다 |
| 검증 상태 | 내부 검토 (DOM 확인) |

**축에 `현재 단계`가 더해졌다.** `감정평가 (사전)` 단계의 환자, `프로세스 종료` 단계의 환자를 바로 거를 수 있다.

- **이 축은 분석 화면의 차트에는 올리지 않는다.** 차트 축을 하나 더 두면 '강조된 구간의 합이 KPI와 같다'(4.3.1절)는 관계를 읽을 자리가 늘어나고, 프로세스 상태(진행 중/완료…)와 뜻이 겹쳐 보인다. 축 정의에 `chart: false`를 두어 리스트·패널만 쓴다.
- 구간 순서는 프로세스의 단계 순서를 그대로 따른다.

#### 4.4.4. 필터 버튼의 색

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | Figma는 `필터` 버튼을 accent로 고정하고 있으나, 이는 accent 용법 3가지 어디에도 해당하지 않는다 |
| 위반 원칙 | Consistency (3.1절 accent 동결) |
| 변경 후 | **걸린 필터가 있을 때만 accent다.** '선택 상태'로 해석했다 |
| 검증 상태 | 내부 검토 (Figma와의 차이를 의도적으로 둔 항목) |

> **확인 필요:** 필터·정렬 팝오버는 Figma에 열린 상태가 없어 초안이다.

### 4.5. 환자 상세

환자 정보 → 프로세스 스테퍼 → 탭 카드. 우측 패널을 쓰지 않는다(4.0.1절).
진입 경로는 넷이다 — 아젠다 환자 블록 · 캘린더 팝오버 · 리스트 행 · 우측 환자 패널.

상단(정보 + 스테퍼)은 탭과 무관하게 늘 같고 **하단 카드만 탭으로 바뀐다.** 탭은 `프로세스 히스토리` / `핵심 지표` / `개인 메모` 3개다.

#### 4.5.1. 스테퍼의 노드 표현

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 단계 노드에 순서 숫자를 넣으면 상태(완료/진행/대기)와 순서가 한 자리에서 경쟁한다 |
| 위반 원칙 | Minimalism |
| 변경 후 | **노드 글리프는 상태만 표시한다.** 완료 = 체크, 진행 중 = accent fill, 대기 = 빈 점선 원. 순서는 노드의 배치 순서가 이미 표현한다. 연결선은 지나온 구간 실선, 앞으로 갈 구간 점선 |
| 거부된 대안 | 순서 숫자 표기 — 순서는 배치로 이미 알 수 있으므로 중복 |
| 검증 상태 | 내부 검토 |

**스테퍼 노드는 모두 누를 수 있다.**

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 스테퍼가 상태만 보여주는 그림이면, 이미 끝낸 단계의 내용을 다시 보려면 프로세스를 처음부터 훑어야 한다 |
| 위반 원칙 | Efficiency |
| 변경 전 | 노드는 표시 전용. 진입은 '이어하기' 버튼 하나뿐 |
| 변경 후 | **완료·진행 중 노드가 그 단계로 가는 진입점이다.** 대기 노드만 갈 수 없다 — 아직 도달하지 않은 단계에 임의로 들어가면 시스템 안정성이 깨진다(4.1.6절 배치 단계 결정과 같은 이유). 대기 노드를 누르면 **비활성 사유 콜아웃**이 뜬다(3.8절) |
| 거부된 대안 | 대기 노드를 완전히 비활성 — 반응이 없으면 고장으로 읽힌다. / 대기 노드도 진입 허용 — 도달하지 않은 단계의 데이터가 없다 |
| 검증 상태 | 내부 검토 |

노드 전체가 터치 대상이다. 원만 누르게 하면 라벨을 눌렀을 때 헛돈다.

**프로세스로 들어가는 버튼은 상태에 따라 라벨과 목적지가 바뀐다.**

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 스테퍼 노드로 들어갈 수는 있지만, 지금 무엇을 해야 하는지 한눈에 알리는 자리가 없다. 시작 전 환자는 특히 프로세스를 시작하는 입구가 화면에 없었다 |
| 위반 원칙 | Efficiency, Safety and Trust — 입구가 없으면 다음 행동을 알 수 없다 |
| 변경 후 | 스테퍼 카드 머리 오른쪽에 진입 버튼을 둔다. **시작 전 → `프로세스 시작`(0단계), 진행 중 → `이어하기`(현재 단계), 중단 → `프로세스 재시작`(0단계).** 완료 환자만 갈 곳이 없어 버튼을 두지 않는다. 화면의 주 행동이므로 채움 버튼이다 |
| 거부된 대안 | 완료 환자에게도 비활성 버튼 노출 — 3.8절대로면 비활성에는 사유를 말해야 하는데, '끝난 프로세스'는 무엇을 채우면 열리는지 말할 것이 없다. 노드는 모두 완료라 되짚어 볼 길이 이미 열려 있다. / 중단 프로세스를 끊긴 단계에서 이어붙임 — 중단 시점의 데이터가 어디까지 유효한지 알 수 없다. **처음부터 다시 건다**(4.6.1절 확인 문구 "할당 후 변경하려면 프로세스를 재시작해야 합니다"와 같은 이야기다) |
| 검증 상태 | 내부 검토 (DOM 확인) |

**아직 프로세스가 붙지 않은 환자에게는 프로세스 이름을 지어내지 않는다.** 시작 전 환자는 `미할당`으로 표기한다. 할당이 끝나면 그때 붙은 프로세스의 이름을 그대로 쓴다(4.6.1절).

- **시작 전 환자는 완료된 단계가 하나도 없고, 첫 단계(프로세스 시작)가 '진행 중'이다.** 첫 단계까지 완료로 칠해서도 안 되지만, 전부 대기로 두어서도 안 된다 — 프로세스 시작이 지금 할 차례인데 대기로 두면 어느 노드도 열리지 않아 **프로세스를 시작할 길 자체가 사라진다.**
- 완료·중단 환자는 '진행 중' 단계가 없다.
- 이 판정은 환자 상세의 큰 스테퍼와 코어 프로세스의 컴팩트 스테퍼가 **같은 함수 하나**를 쓴다. 두 곳에 복제해 두었더니 위 결함이 양쪽에 똑같이 생겼다(5.2절).
- **프로세스 이름은 진단을 따른다.** 목업이 특정 진단 한 명분이라 그대로 쓰면 다른 진단의 환자에게 잘못된 프로세스명이 붙는다.

#### 4.5.2. 추이 그래프

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 지표마다 값의 범위가 달라 눈금을 하나로 고정하면 일부 지표의 값이 눈금 밖으로 나간다 |
| 위반 원칙 | Safety and Trust (데이터 왜곡) |
| 변경 후 | **눈금은 데이터를 가운데 두고 화면이 계산한다.** 눈금과 점이 같은 좌표계를 쓴다 |
| 거부된 대안 | 눈금 고정 — 범위를 벗어나는 지표가 그려지지 않는다. / 점을 절대 좌표로 배치 — 데이터가 바뀔 때 눈금과 어긋난다 |
| 검증 상태 | 내부 검토 (두 개 지표에서 Figma 실측 눈금과 일치) |

Key data 카드를 누르면 아래 그래프가 그 지표로 바뀐다.

#### 4.5.4. 펼쳐지는 목록의 경계

프로세스 히스토리는 행을 누르면 아래로 상세가 펼쳐진다.

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 머리 행과 펼쳐진 본문을 각각 온전한 라운드 상자로 두면, 맞닿는 자리에 테두리가 두 줄로 겹치고 모서리가 네 개 생긴다. 정작 중요하지 않은 경계가 화면에서 가장 눈에 띄는 선이 된다 |
| 위반 원칙 | Minimalism — 하나의 덩어리를 둘로 보이게 하는 선이 추가된다 |
| 변경 전 | 머리와 본문이 각각 라운드 8 + 전체 테두리. 겹침을 막으려 본문을 1px 끌어올림 |
| 변경 후 | **펼쳐지면 둘이 한 상자가 된다.** 머리는 아래쪽 라운드와 테두리를 걷고 본문은 위쪽을 걷는다. 둘 사이는 **배경색 차이만으로** 나뉜다. 테두리 색도 accent 하나로 통일한다 |
| 거부된 대안 | 겹친 선을 음수 마진으로 상쇄 — 선은 한 줄이 되지만 모서리 네 개는 그대로 남는다. / 본문의 테두리를 없앰 — 선택된 덩어리의 범위가 아래에서 끊긴다 |
| 검증 상태 | 내부 검토 (DOM 실측: 머리 `1px 0`, 본문 `0 1px`, 사이 간격 0) |

이 처리는 접었다 펴는 목록 전반에 적용한다.

> **확인 필요:** 프로세스 단계 구성·이력·평가 지표는 대부분 임시값이다. 두 개 지표의 추이만 Figma 실측이고 나머지와 종료된 프로세스의 내용은 임의로 채웠다. 상세 치유 프로세스 정보가 확정되면 교체한다.

#### 4.5.3. 개인 메모 탭

Figma `188:5004`(목록) · `189:8675`(편집 중) · `190:8960`(삭제 확인) 세 상태로 구성된다.

- **목록** — `새 메모` 버튼 + 검색바, 그 아래 메모 카드 2열. 카드는 날짜 + 맥락 태그(어느 단계·회차에서 작성되었는지) + 편집·삭제 액션(각각 터치 타깃 규격 충족) + 본문으로 구성된다. 검색은 본문과 날짜를 함께 본다.
  - **본문은 두 줄까지 보여준다.** Figma는 한 줄이지만, 한 줄이면 긴 메모의 뒷부분을 편집 화면에 들어가야만 읽을 수 있다. 읽으려고 편집을 여는 것은 미저장 경고까지 끌어들이는 경로다
  - **본문과 맥락 태그의 글자 크기를 한 단계씩 올렸다.** Figma 값 그대로는 카드에서 가장 중요한 본문이 화면에서 가장 작은 글자가 된다. 날짜 > 본문 > 태그의 위계는 유지된다
  - **카드의 좌우 패딩은 대칭이다.** Figma는 우측이 좁은데, 이는 액션 아이콘의 터치 영역이 만드는 여백을 감안한 값이다. 패딩을 대칭으로 두고 아이콘 묶음만 음수 마진으로 밀어 아이콘의 시각 위치는 Figma와 맞추면서, 본문·입력 영역의 좌우 여백이 갈리지 않게 했다
- **편집** — 카드 하나가 편집 상태로 커진다. 헤더의 액션이 `편집 중` 표시로 바뀌고, 본문이 입력 영역이 되며 하단에 취소 + 저장 버튼이 붙는다. **테두리가 accent로 바뀐다** — 3.1절 '선택 상태는 배경만으로 표현하지 않는다'의 적용이며, 편집 중인 카드가 어느 것인지가 목록에서 즉시 보여야 하기 때문이다.
- **삭제** — 스크림 + 확인 alert. 어느 메모가 삭제되는지를 날짜·맥락으로 특정하고, 복구할 수 없다는 사실을 못박는다.

**새 메모도 같은 편집 카드다.** 별도의 입력 화면을 두지 않고 목록 맨 앞에 카드 하나가 편집 상태로 열린다. 쓰는 자리와 읽는 자리가 같아 맥락이 끊기지 않는다(Consistency).

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 메모의 맥락 태그(`프로그램 수행 · 4회차`)를 누가 정하는가 |
| 위반 원칙 | Efficiency — 매번 고르게 하면 조작이 늘고, 잘못 고르면 나중에 읽을 때 단서가 어긋난다 |
| 변경 후 | **새 메모의 맥락은 환자의 현재 단계를 따른다.** 고르는 항목이 아니다 |
| 거부된 대안 | 상담사가 직접 선택 — 4.1.6절 배치 단계 결정과 같은 이유로, 앱이 이미 아는 값을 다시 묻지 않는다 |
| 검증 상태 | 내부 검토 |

메모는 3.6절 오토세이브 없음 규칙을 탄다. **편집 중 이탈은 전부 미저장 경고를 거친다** — 탭 전환 · 다른 메모 편집 · 새 메모 · 삭제 · 화면 이탈(버튼과 라우터 양쪽). 경고를 한 지점에 모으지 않으면 어느 한 경로만 빠져나간다. 삭제는 되돌릴 수 없으므로 확인 모달을 반드시 거친다.

> Figma의 삭제 확인 모달에서 확정 버튼의 텍스트 레이어 이름이 다른 화면의 것(`프로그램 처방으로 이동`)으로 남아 있었으나, 실제 문자열은 `삭제`임을 확인했다. 같은 노드의 텍스트 폭이 두 글자분이고 화살표 아이콘도 숨김 처리되어 있다. **해소됨.**

### 4.6. 코어 프로세스

`[작성 예정 — 미착수]`

프로세스 화면 공통 규칙은 3.2절(우하단 고정 Primary CTA, 전제조건 미충족 시 비활성)을 따른다. 진입점은 환자 상세 스테퍼의 '이어하기' 버튼이다.

**단계는 환자에게 붙은 프로세스 정의가 정한다**(4.8.6절). 노드 수도 순서도 정의마다 다르므로 화면이 단계 목록을 상수로 들지 않는다(`stepsOf`). **프로세스 시작과 종료만 고정된 양끝**이다 — 저작에서 다루는 노드가 아니라 프로세스를 붙이고 끝내는 자리다. 스테퍼 · 단계 본문 · 다음 단계 라벨 · 환자 레코드의 `status` 문자열이 모두 이 목록 하나를 센다.

- 단계 본문은 **번호가 아니라 노드의 종류**로 갈린다. 번호로 갈리면 정의가 바뀔 때마다 화면이 어긋난다.
- 감정평가의 시점(사전 · 사후)도 노드가 들고 있다. `종료 확정`은 사후 노드에서만 나온다.
- 스테퍼의 연결선은 늘고 줄어 폭을 맞춘다. 노드 수가 정의마다 다르기 때문이다.

**모든 단계 화면이 같은 머리를 쓴다** — 환자 정보 + **컴팩트 스테퍼** + '환자 상세'로 돌아가는 버튼. 스테퍼가 곧 단계 이동 장치이므로, 환자 상세의 큰 스테퍼와 **같은 규칙**(완료·진행 중은 갈 수 있고 대기는 못 간다)을 그대로 쓴다. 머리를 화면마다 다시 그리면 규칙이 여러 곳으로 갈라진다.

- 단계는 **경로에 들어간다.** 새로고침·뒤로가기가 같은 단계로 돌아와야 한다.
- 지금 보고 있는 단계의 라벨은 accent다 — 3.1절 용법 '현재 위치 마커'.
- 프로세스를 다루는 화면이므로 **우측 환자 패널이 없다**(4.0.1절). Figma 본문 폭도 패널 자리 없는 값이다.

#### 4.6.1. 프로세스 개시

치유 프로세스 리스트에서 이 환자에게 적용할 프로세스를 고르는 화면이다(Figma `148:7242`). 진단으로 거른 칩 + 검색 + 정렬, 그 아래 표(프로세스명 · 증상명 · 작성자 · 작성일). **구버전은 흐리게 내리되 목록에서 빼지 않는다** — 과거에 쓰던 프로세스를 확인할 수 있어야 한다.

##### 진단 칩은 두 개뿐이다

**문제 정의.** 라이브러리에는 진단이 여럿인 프로세스가 섞여 있다. 진단 축을 전부 칩으로 펼치면 진단이 늘어날 때마다 칩 행이 늘어난다.

**결정.** 칩은 **환자의 진단**과 **전체** 둘뿐이고 기본값은 환자의 진단이다. 이 화면은 라이브러리를 훑는 곳이 아니라 **이 환자에게 붙일 것을 고르는 곳**이라, 기본 상태가 곧 맞는 답이어야 한다. '전체'로 넓히면 다른 진단의 프로세스도 보이고, 그것을 고르면 경고가 붙는다.

**거부된 대안.** ① 진단 축 전체를 칩으로(4.4절 필터와 중복되고, 환자와 무관한 선택지가 기본으로 보인다) ② 다른 진단을 아예 감춤(동반이환·시연처럼 필요한 경우를 막는다. 3.1절 안전성 원칙은 *막는 것*이 아니라 *알리는 것*으로 푸는 쪽이 위계상 앞선다).

##### 진단이 다른 프로세스에는 경고를 붙이되 막지 않는다

**문제 정의.** 환자 진단과 다른 프로세스를 고르는 것은 대개 실수지만 항상 실수는 아니다.

**결정.** 상세 모달에서 **세 자리**에 경고를 붙인다(Figma `172:4483` · `173:5793`). ① 진단 칩이 경고색 테두리 + 경고 아이콘 ② '프로세스 구성' 머리 오른쪽에 `환자 진단(OO)과 다른 프로세스입니다` ③ 확인 문구의 진단 이름이 경고색 볼드. 확정 버튼 라벨도 `할당 확정` → **`그래도 할당`**으로 바뀐다 — 같은 버튼이 같은 말을 하면 무엇이 다른지 알 수 없다.

**거부된 대안.** ① 할당 버튼 비활성(필요한 경우를 막는다) ② 경고를 한 자리에만(고른 순간·확정 직전 중 어느 한쪽에서만 보인다).

##### 할당은 확인을 거친다

**문제 정의.** 할당은 되돌리려면 프로세스를 재시작해야 하는 조작이다.

**결정.** 목록 행 탭 → 상세 모달 → `할당하기` → **버튼 행이 확인 상태로 바뀌고**(무엇이 확정되는지 한 줄) → `할당 확정`. 3.6절 '저장은 명시적 조작으로만'의 연장이다. **`취소`는 모달을 닫지 않고 훑어보던 자리로 돌아간다** — 중복 경고의 `돌아가기`와 같은 문법이다(4.0.4절). 닫으려면 `닫기` · 스크림 탭 · 뒤로가기를 쓴다.

**거부된 대안.** ① 목록 행에 할당 버튼 직접 노출(모든 행이 확정 버튼을 갖게 되어 오조작이 쉽다) ② 확인을 별도 alert 모달로(대형 모달 위에 모달이 겹치고, 무엇을 할당하는지 보면서 확인할 수 없다).

##### 단계 아코디언은 머리와 본문이 한 상자다

Figma는 펼친 머리와 본문을 각각 온전한 상자로 두었으나, 4.5.4절 규칙(머리 `rounded-t`·`border-b-0` / 본문 `rounded-b`·`border-t-0`, 테두리 색 통일, 사이는 배경색 차이로만 구분)을 적용했다. **의도적으로 Figma와 다르게 둔 것이다.** 펼친 머리는 선택 상태이므로 테두리·배경이 accent이고, 본문은 같은 accent 테두리에 카드 배경이다.

모달 높이는 **480 고정**이다. 아코디언을 여닫을 때마다 상자와 버튼 행이 움직이면 다음 조작 지점을 다시 찾아야 한다.

##### 할당의 결과

할당이 끝나면 환자의 프로세스 상태가 `진행 중`, 현재 단계가 `감정평가 (사전)`이 되고 화면은 **다음 단계로 넘어간다.** 방금 끝낸 단계에 머무르면 무엇을 더 해야 하는지 알 수 없다. 스테퍼의 '프로세스 시작' 노드는 완료(체크)로 바뀐다.

**이력도 함께 바뀐다.** 돌아가던 프로세스는 `종료`로 닫히며 종료일과 사유(`중단 후 재시작` / `재할당으로 종료`)가 마지막 줄로 남고, 새로 할당한 프로세스가 `진행 중` 항목으로 열린다. 끊긴 자리에 이어붙이지 않고 새 항목을 여는 것이 재시작의 정의다(4.5.1절). 이력 목업은 모든 환자가 함께 보는 것이라 **원본을 고치지 않는다** — 환자별 변경분만 따로 쌓고 읽는 시점에 합친다(5.2절).

> **미해결:** 이미 프로세스가 할당된 환자가 이 화면에 다시 들어왔을 때의 처리. 현재는 할당된 행을 선택 상태로 표시하고 재할당을 그대로 허용한다. Figma에 해당 상태가 없다. 6.2절 21번 항목 참조.

> **미해결:** 정렬 선택지 구성(현재 `최신순`(기본) · `오래된순` · `이름순`)과 '프로그램 처방 · 프로그램 수행' 단계를 펼쳤을 때의 내용은 Figma 근거가 없는 초안이다. 6.2절 7번 항목 참조.

#### 4.6.2. 감정평가 (사전 · 사후)

**사전과 사후는 같은 화면이다.**

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 사전(1단계)과 사후(4단계)는 보는 설문도 판정 규칙도 같고 시점만 다르다. 화면을 둘로 두면 같은 규칙이 두 곳에 복제된다 |
| 위반 원칙 | Consistency |
| 변경 후 | **한 화면이 단계 번호로 시점을 정한다.** 화면 안의 `사전`/`사후` 칩으로 시점을 오갈 수 있되, **아직 도달하지 않은 시점은 열 수 없다** — 사전 단계에서 사후 설문을 열면 순서가 뒤집힌다. 지나온 시점은 기록이므로 되돌아가 볼 수 있다(스테퍼 노드와 같은 규칙, 4.5.1절). 막힌 칩을 누르면 비활성 사유 콜아웃이 뜬다 |
| 거부된 대안 | 사전·사후 화면 분리 — 규칙이 복제된다. / 시점 칩 없이 단계로만 고정 — 사후 단계에서 사전 결과를 나란히 볼 수 없다 |
| 검증 상태 | 내부 검토 (DOM 확인) |

**설문 목록은 프로세스가 정한다.** 화면이 목록을 따로 들지 않고 할당된 프로세스의 감정평가 단계 구성을 그대로 읽는다(4.6.1절). 그래서 PTSD 프로세스는 4종, 게임과몰입 프로세스는 7종이 뜬다.

- 설문마다 **핵심/보조**와 **진단/공통** 두 배지가 붙는다. 핵심은 그 프로세스의 판정 근거이고 보조는 참고다. 핵심만 채운 배지로 두어 위계를 드러낸다.
- 점수는 **막대와 컷오프 마커**를 함께 보여준다. 점수 하나만으로는 높은지 낮은지 알 수 없다.
- 아직 작성되지 않은 설문은 값 자리를 `-`로 두고 내용을 흐리게 내린다. 없는 값을 있는 것처럼 그리지 않는다(4.3.2절 0명 막대와 같은 이유).
- **작성완료된 설문은 그 단계에 있는 동안만 다시 열 수 있다.** 막으면 잘못 찍은 응답을 되돌릴 길이 없지만, **다음 단계로 넘어간 뒤에는 잠긴다** — 그 뒤 단계가 이미 참조한 점수(프로그램 처방의 등급·감정 지표)와 어긋나기 때문이다. 지난 단계에서 누르면 사유 콜아웃이 뜨고 다음 단계 버튼도 함께 잠긴다.
- 다음 단계로 가는 버튼은 **모든 설문이 작성되어야 활성**이다(3.2절 전제조건 규칙). 비활성인 채 누르면 몇 종이 남았는지 말한다.
- 버튼 라벨은 **다음 단계의 이름을 따른다** — 사전이면 '프로그램 처방으로 이동', 사후면 '프로세스 종료로 이동'이다. 라벨을 고정하면 사후 단계에서 틀린 곳을 가리킨다.

감정평가는 **척도 선택·결과 확인(상담사)** 과 **설문 응답(환자)** 두 단계로 나뉜다. 두 단계는 조작 주체가 다르므로 셸 구성도 다르다.

| 단계 | 조작자 | 셸 |
| --- | --- | --- |
| 척도 선택 / 결과 확인 | 상담사 | 3분할 셸 유지 |
| **설문 수행** | **환자** | **좌측 내비 · 우측 패널 모두 감춤** (4.0.1절) |

설문 수행 화면은 전체 화면 중 **환자가 상담사의 태블릿을 직접 조작하는 유일한 지점**이다. 근거와 거부된 대안은 4.0.1절에 기술한다.

설문 응답도 3.6절 저장 규칙을 탄다 — 오토세이브를 전제하지 않으므로, 응답 도중 이탈 시 데이터가 소실되지 않도록 이탈 경로 자체를 제거하는 것이 위 셸 결정의 목적 중 하나다.

**설문 종료와 태블릿 회수**

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 환자가 임의로 종료할 수 있으면 미완 제출이 발생한다. 반대로 상담사만 종료할 수 있으면 그 조작이 환자 화면에 노출되어서는 안 된다 |
| 위반 원칙 | Safety and Trust — 미완 제출은 임상 데이터의 결손이다 |
| 변경 후 | **환자가 종료하는 유일한 경로는 제출 버튼이다.** 제출이 완료되면 **완료 알림 전용 화면**으로 전환된다. 이 화면에는 설문 내용도, 상담사용 탐색 경로도 없다 |
| 거부된 대안 | 환자가 임의 종료 후 상담사 화면으로 복귀 — 미완 상태로 셸이 노출된다. / 상담사만 종료 — 종료 조작이 환자 화면에 노출되거나, 상담사가 태블릿을 돌려받을 때까지 설문 화면이 그대로 남는다 |
| 검증 상태 | 내부 검토 (DOM 확인) |

완료 알림 화면은 **환자에게는 종료 신호이자, 상담사에게는 회수 신호**다. 이 화면이 떠 있는 동안 설문 화면과 마찬가지로 셸을 걷은 상태를 유지한다 — 태블릿이 아직 환자 손에 있을 수 있기 때문이다. 상담사용 화면으로의 복귀는 이 화면의 명시적 조작으로만 이루어진다.

**중간에 멈춘 설문에도 나갈 길이 있어야 한다.**

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 제출은 모든 문항을 채워야 가능하고 화면에는 나가기 버튼이 없다. 환자가 중간에 그만두면 그 설문은 아무 데도 갈 수 없다 |
| 위반 원칙 | Safety and Trust — 되돌릴 수 없는 막다른 화면이 된다 |
| 변경 후 | **뒤로가기가 3버튼 경고로 갈라진다**: `저장하지 않고 나가기` / `임시 저장하고 나가기` / `계속 응답`. 3.6절의 미저장 이탈 경고와 같은 문법·같은 배치다(파괴적인 쪽을 왼쪽에 텍스트로, 기본 자리는 '계속 응답') |
| 거부된 대안 | 화면에 상시 나가기 버튼 — 환자가 무심코 누른다. 뒤로가기 뒤에 두면 나가는 데 두 번의 명시적 조작이 필요하다. / 제출만 유일한 출구로 유지 — 중간에 멈춘 설문이 막다른 길이 된다 |
| 검증 상태 | 내부 검토 (DOM 확인) |

임시 저장은 **저장했다는 사실을 남기는** 조작이다. 그 사실이 남아야 감정평가 목록이 `작성 중`(응답 수까지)과 `아직 손대지 않음`을 구분하고, 나가기 경고도 무엇이 사라지는지를 다르게 말할 수 있다.

복귀 조작은 **화면 아래에 따로 떨어뜨린 테두리 버튼**으로 두었다(`상담사 화면으로 돌아가기`). 완료 문구와 시각적으로 붙여 두면 환자가 확인 버튼으로 읽고 누른다.

**설문 수행 화면의 뒤로가기 경고는 history 엔트리를 갖지 않는다.** 이것이 4.0.4절의 모달 규칙에서 갈라지는 유일한 지점이다 — 이 경고 자체가 뒤로가기에 대한 응답이라, 엔트리를 만들면 *경고를 닫는 뒤로가기*와 *화면을 나가려는 뒤로가기*가 같은 제스처를 두고 다툰다. 실제로 공용 모달 셸로 만들었더니 경고가 닫히지 않았다. 이탈 차단은 라우터 가드 한 자리가 맡고, 경고는 그 응답으로만 뜬다.

> **확인 필요:** 설문 문항·설명·척도는 전부 임의로 지은 목업이다. 척도 이름과 문항 수는 실제 도구를 흉내 냈지만 문장은 원문이 아니다. 실제 문항은 저작권과 표준화 절차가 걸린 자료이므로 확정되면 통째로 교체한다. 6.2절 23번 항목 참조.
>
> **미해결:** 결과 '출력' 기능은 버튼만 있고 동작하지 않는다. 6.2절 24번 항목 참조.
>
> **미해결:** 척도 항목 수의 가변 여부가 미확정이다. 6.2절 1번 항목 참조.

##### 생체신호 측정 (웹 구버전 이식)

감정평가 자리에서 HRV·fNIRS 측정값을 올린다. **측정 장비와 백엔드에 묶인 기능이라 모습만 옮겼다** — 첨부한 파일은 이름만 남기고 내용을 읽지 않으며, fNIRS 활성화 지도는 자리만 잡아 둔다.

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 생체신호를 재는지 여부가 환자·프로세스마다 갈린다. 버튼을 누구에게 보일 것인가 |
| 위반 원칙 | Safety and Trust (3.8절 — 무반응은 고장으로 읽힌다) |
| 변경 후 | **프로세스가 정한다**(정의의 `bio`). 설문 구성을 프로세스가 정하는 것과 같은 자리다. 버튼은 **언제나 보이되**, 재지 않는 프로세스에서는 흐리게 두고 누르면 사유 콜아웃이 뜬다 |
| 거부된 대안 | ① 버튼을 감추기 — 이 프로세스에 그런 단계가 있는지조차 알 수 없다. ② 프로세스 개시 화면에서 상담사가 체크 — 프로세스 정의가 이미 단계 구성을 들고 있어 정의가 정하는 편이 일관된다(⚠️ 상담사가 켜고 끌 수 있어야 하는지는 확인 필요) |
| 검증 상태 | 내부 검토 (DOM 확인) |

- **시점을 물려받는다.** 사전에 잰 값과 사후에 잰 값이 같은 자리에 섞이면 전후 비교가 성립하지 않는다
- 무거운 콘텐츠라 대형 모달(690×480)이고, **머리와 HRV·fNIRS 전환은 고정**이다 — 폼이 길어 셸이 통째로 스크롤되면 전환이 화면 밖으로 밀려난다
- **임상 범위를 벗어난 값은 막지 않고 알린다.** 장비가 그렇게 읽었을 수도 있어 상담사의 판단을 대신하지 않는다. 저장 버튼 옆에 몇 개가 벗어났는지 적는다
- 저장은 명시적 조작이고(3.6절) **채운 항목만** 남는다. 하나도 채우지 않으면 버튼이 비활성이다

#### 4.6.3. 프로그램 처방

**처방할 프로그램은 프로세스 정의가 미리 고르지 않는다.** 처방은 이 단계에서 환자를 보고 상담사가 하는 일이다. 정의를 만드는 사람이 후보를 골라두면 처방을 대신하는 셈이고, 프로그램 목록이 바뀌면 그 선택이 낡는다. 저작도구의 처방 노드는 **그 증상에서 처방할 수 있는 프로그램을 보여주기만** 한다(4.8.6절).

감정평가 결과를 근거로 이 환자에게 붙일 인문 프로그램을 고르는 화면이다(Figma `148:8145` · `178:3788` · `179:4283` · `180:4914`).

**한 화면이 탭 둘로 갈린다.**

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 프로그램을 고르려면 감정평가 결과를 봐야 하는데, 결과와 목록을 다른 화면에 두면 고르는 도중 근거를 다시 보려고 화면을 나가야 한다 |
| 위반 원칙 | Efficiency, Safety and Trust — 근거 없이 고르게 된다 |
| 변경 후 | 한 화면에 **`감정평가 정보` / `프로그램 선택`** 두 탭을 둔다. 탭은 탐색이므로 상태를 바꾸지 않는다(3.5절). 컨트롤은 좌측 하단 테마 토글과 같은 세그먼트 토글이고, 선택된 쪽만 카드 표면 + accent 테두리를 갖는다 |
| 거부된 대안 | 결과를 모달로 겹쳐 보여줌 — 고르는 동안 계속 여닫아야 한다. / 결과를 목록 위에 요약만 표시 — 척도별 점수와 등급이 들어갈 자리가 없다 |
| 검증 상태 | 내부 검토 (DOM 확인) |

**감정평가 정보 탭**은 사전 감정평가(4.6.2절)가 남긴 응답을 **다시 계산하지 않고 읽는다.** 두 화면이 다른 점수를 보여주면 어느 쪽이 맞는지 알 수 없다.

- 척도마다 **등급 배지**가 붙는다: `고위험` / `중증도` / `정상` / `미작성`. **고위험만 경고색**이다 — 악화 표현 전용 규칙(3.1절)이고, 나머지는 중립색 테두리로 세기를 낮춘다.
- **값이 없는 것을 `정상`으로 두지 않는다.** 안 한 것과 괜찮은 것이 같아 보인다. `미작성`으로 갈라 점수 자리도 `-`로 둔다.
- 오른쪽은 **감정 지표** 다섯 축의 세로 막대다. `0–100 정규화`이고 **높을수록 양호**임을 머리에 밝힌다 — 방향을 적지 않으면 높은 막대가 좋은 것인지 나쁜 것인지 알 수 없다.

**프로그램 선택 탭**은 검색 · 정렬 · 필터 넷(치유대상감정 · 주제어 · 운영형태 · 기관) + 프로그램 행이다.

- 목록에 오르는 것은 **이 환자의 진단에 맞는 프로그램뿐**이다. 프로세스 할당(4.6.1절)과 달리 다른 진단을 고르는 길을 두지 않았다 — 프로세스는 환자에게 붙는 뼈대라 예외가 필요하지만, 프로그램은 그 프로세스 안에서 고르는 내용물이라 이미 진단이 정해져 있다.
- **고른 행에는 체크가 붙는다.** 배경과 테두리만으로는 선택이 잘 보이지 않는다(3.1절).
- 하단에 **무엇을 골랐는지 한 줄로** 남기고, 고르기 전에는 다음 단계 버튼이 비활성이다. 비활성인 채 누르면 사유 콜아웃이 뜬다.
- 필터 팝오버의 첫 줄은 언제나 `전체`다. 걸린 필터를 푸는 길이 없으면 막다른 길이 된다.

**세션 상세의 내용은 붙은 세션 활동에서 온다**(4.8.9절). PHASE와 활동 문구를 생성기가 그럴듯하게 채우던 것을 걷었다 — 활동을 붙이는 길이 생긴 뒤로는 **그것이 지어낸 값임을 화면이 알 수 없다.** 활동이 붙지 않은 회차는 비워 두고 `이 회차에 붙은 세션 활동이 없습니다`라고 말한다(프로그램 수행 화면도 같다). Figma에 문구가 있던 한 단계(마음챙김 1세션 PHASE 1)는 **활동 정의로 옮겨** 그대로 남겼다.

**프로그램 상세와 세션 상세는 한 모달이다.**

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 세션 상세를 별도 모달로 겹쳐 띄우면 history가 두 겹이 되어 뒤로가기를 두 번 눌러야 목록으로 돌아온다 |
| 위반 원칙 | Safety and Trust (4.0.4절 history 규칙) |
| 변경 후 | **같은 상자 안에서 내용만 바뀐다.** 세션을 보는 동안 머리의 닫기(X)가 뒤로가기(chevron-left)로 바뀐다. Figma도 그렇게 그렸다 |
| 거부된 대안 | 모달 위에 모달 — history가 겹친다. / 세션 상세를 화면으로 분리 — 프로그램을 고르던 맥락이 사라진다 |
| 검증 상태 | 내부 검토 (DOM 확인) |

세션 안에서는 **PHASE를 페이지로 넘긴다.** 다섯 PHASE가 한 세션의 흐름이라 목록으로 늘어놓지 않고, 지금 어디인지를 `1/5`로 남긴다. 마지막 PHASE에서는 버튼이 `세션 목록`으로 바뀌어 되돌아갈 자리를 준다.

> **확인 필요:** 등급 판정 규칙은 Figma 4건에서 **역산한 것**이다(컷오프 초과 + 핵심/보조). 실제 판정 기준은 척도마다 다르므로 확인이 필요하다. 6.2절 25번 항목 참조.
>
> **확인 필요:** 감정 지표 다섯 축의 값은 Figma 실측을 그대로 둔 임시값이다. 설문 점수에서 이 축을 뽑는 규칙이 확인되지 않았다. 6.2절 26번 항목 참조.
>
> **확인 필요:** 프로그램·세션·PHASE의 내용은 임의로 지은 목업이다. Figma에 실제로 적힌 것은 프로그램 4건의 요약 행과 한 프로그램의 세션 이름, 1세션 PHASE 1의 활동 문구뿐이다. 6.2절 27번 항목 참조.

#### 4.6.4. 프로그램 수행

처방된 프로그램의 회차를 하나씩 진행하며 그때의 관찰을 남기는 화면이다(Figma `148:8311`). 좌측은 회차 목록과 진행률, 우측은 고른 회차의 내용과 수행 내역이다.

**두 칸을 한 화면에 둔다.** 기록하는 도중 '지금 몇 회차인지'와 '무엇을 하기로 한 회차인지'를 다시 보려고 화면을 나가면 안 된다 — 4.6.3절 탭 결정과 같은 이유다.

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 회차는 여럿이고 각각 상태(완료/진행 중/대기)와 기록을 갖는다. 상태를 어디에 표시할지, 무엇을 보고 있는지를 어떻게 구분할지가 겹친다 |
| 위반 원칙 | Consistency — accent 용법이 겹쳐 읽힌다(3.1절) |
| 변경 후 | **선택은 행 전체의 accent 테두리**가, **진행 상태는 행 오른쪽의 상태 배지**가 말한다. 대개 둘이 같은 행이지만, 지난 회차의 기록을 다시 볼 때 갈린다 — 그때 무엇을 보고 있는지와 어디까지 왔는지가 각각 보여야 한다 |
| 거부된 대안 | 진행 중인 회차만 열고 나머지는 잠금 — 지난 회차의 기록을 확인할 길이 없다 |
| 검증 상태 | 내부 검토 (DOM 확인) |

- 상태 배지 셋: **완료**(체크 + 중립 표면) / **진행 중**(accent 채움) / **대기**(흐린 표면). 완료는 개선 표현이므로 경고색을 쓰지 않는다(3.1절).
- 아직 오지 않은 회차는 **기록할 것이 없다.** 수행 내역 입력이 비활성이고, 다음 회차로 넘기는 버튼을 누르면 사유 콜아웃이 뜬다.
- **수행 내역은 오토세이브하지 않는다**(3.6절). 저장하면 저장한 시각이 남고, 저장하지 않은 내용이 있으면 그렇다고 말한다.
- 주 행동은 **`저장 후 N회차로`**다. 저장과 회차 완료를 한 조작으로 묶는 이유는, 회차를 마쳤다는 사실과 그때의 기록이 같은 조작에서 나와야 하기 때문이다. 마지막 회차에서는 갈 회차가 없으므로 라벨이 `저장 후 감정평가로`가 되고 다음 단계로 넘어간다.
- 회차의 **이름과 개수는 처방된 프로그램이 정한다**(4.6.3절). 화면이 목록을 따로 들지 않는다.

**회차 날짜는 일정(4.2절)에서 온다.** 회차를 언제 하는지는 상담사가 잡은 약속이 정하는 값이지, 회차 기록이 스스로 만들어낼 값이 아니다.

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 회차 목록에 붙는 날짜를 어디서 가져올 것인가 |
| 위반 원칙 | Safety and Trust — 같은 회차를 두 화면이 다른 날로 말하면 어느 쪽이 맞는지 알 수 없다 |
| 변경 전 | '주 1회, 지금 회차가 오늘'이라는 규칙으로 화면이 날짜를 만들어냈다. 일정을 아무리 옮겨도 회차 날짜는 그대로였다 |
| 변경 후 | 그 환자의 **환자 일정**에서 가져온다. 끝낸 회차는 지난 진료일을 뒤에서부터, 남은 회차는 앞으로 잡힌 진료일을 앞에서부터 가져간다. 오늘 잡힌 일정은 시각이 지났어도 '남은 것'으로 본다 — 지금 하고 있는 회차다 |
| 약속이 모자랄 때 | 그 회차는 **`일정 미정`**이다. 없는 약속을 있는 것처럼 그리지 않는다 — 잡아야 할 것이 남았다는 뜻이고, 전체 환자 리스트의 '다음 일정 없음'과 같은 판단이다 |
| 거부된 대안 | 회차에 날짜를 따로 저장하고 배치할 때 갱신 — 일정과 회차 두 곳에 같은 사실이 남아 한쪽만 갱신되면 갈라진다. 마지막 진료·다음 일정을 일정에서 뽑는 결정(4.4절)과 같은 이유다 |
| 검증 상태 | 내부 검토 (DOM 확인) |

#### 4.6.5. 사후 감정평가

화면은 사전과 같다(4.6.2절). 시점만 단계 번호가 정한다. **다른 것은 하단 한 줄뿐이다.**

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 사후 단계의 주 버튼은 다음 화면으로 넘어가는 조작인가, 프로세스를 끝내는 조작인가 |
| 위반 원칙 | Safety and Trust > Consistency |
| 변경 후 | **사후의 주 버튼은 `종료 확정`이고, 누르는 순간 프로세스가 종결된다**(Figma `186:6607`). 왼쪽에 무엇이 일어나는지와 현재 시각을 한 줄로 밝힌다 — `<이름> 환자의 프로세스를 종료하시겠습니까? 현재 시각: …` |
| 거부된 대안 | 사전과 같은 `… 단계로 이동` 라벨 — 되돌릴 수 있는 화면 전환으로 읽힌다. 프로세스 종결은 되돌리기가 확인되지 않은 조작이다(6.2절 2번) |
| 검증 상태 | Figma 확인 · DOM 확인 |

**이미 끝난 프로세스에는 종료를 묻지 않는다.** 완료 환자의 사후 화면은 스테퍼로 다시 열 수 있는데, 그때도 확인 문구가 뜨면 아직 끝나지 않은 것으로 읽힌다. 문구가 `이미 종료된 프로세스입니다. <종료 시각> 종료됨`으로 바뀌고, 버튼은 `프로세스 종료 보기`가 되어 결과 화면으로 가는 길이 된다 — 잠긴 채 아무 데도 못 가는 버튼을 남기지 않는다.

종결 조작은 `completeProcess` 한 곳이다. 환자의 프로세스 상태·현재 단계·종료 시각이 함께 바뀌고 이력의 진행 중 항목이 닫힌다. 화면이 환자 레코드를 직접 고치면 이력을 닫는 일이 빠진다.

#### 4.6.6. 프로세스 종결

**마지막 단계는 결과를 보여주는 화면이다**(Figma `148:8564`, 본문 `148:8601`). 여기서 결정하는 것은 없다 — 종결은 앞 단계의 `종료 확정`이 이미 했다. 그래서 하단에 다음 단계 CTA가 없고 종료 시각과 출력만 있다.

구성은 넷이다.

1. **요약 네 칸** — 프로세스 · 기간(시작~종료 · 총 N일) · 처방자 · 프로그램 완료 회차. 세로 1px 구분선으로만 나눈다
2. **`감정평가 사전 · 사후 비교`** 머리 + 두 시점의 날짜
3. **척도 카드 2열** — 코드 · 핵심/보조 배지 · 방향 · 범위 / 사전·사후 막대 / 변화 한 줄
4. **종료 시각 + 출력**

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 사전·사후를 어떻게 나란히 읽히게 할 것인가 |
| 변경 후 | **같은 트랙 위에 두 막대**를 쌓는다. 사전은 흐린 막대(`chart/bar-default`), 사후는 진한 막대다. 길이는 점수/총점이라 두 막대가 같은 자를 쓴다 |
| 값의 출처 | **다시 계산하지 않는다.** 1·4단계가 남긴 응답을 읽는다 — 두 화면이 다른 점수를 보이면 어느 쪽이 맞는지 알 수 없다(4.6.3절과 같은 결정). 회차는 수행 기록에서, 기간·감정평가 날짜는 이력에서 온다 |
| 한쪽이 없을 때 | 막대를 그리지 않고 값 자리는 `-`, 변화는 `비교할 수 없음`이다. 없는 값을 0처럼 그리지 않는다 |
| 변화 표현 | `개선 · N점 감소` / `악화 · N점 증가` / `변화 없음`. **악화만 경고색**이다 — 경고색은 악화 표현 전용이다(3.1절) |
| 검증 상태 | Figma 확인 · DOM 확인(본문 881 · 카드 410 · 요약 55) |

**점수의 방향은 `낮을수록 양호`다.** 종료 화면은 네 척도 모두 `높을수록 양호`로 적었으나, 같은 파일의 프로그램 처방 화면은 컷오프를 넘긴 점수를 고위험으로 판정한다(4.6.3절 `gradeOf`). 둘은 함께 성립할 수 없어 앱이 이미 쓰고 있는 쪽으로 확정했다. 실제 방향은 척도마다 다르므로, 확정되면 설문 정의가 방향을 들고 오게 한다. 6.2절 33번 항목 참조.

> **미해결:** 프로세스 유형별 척도 항목 수의 가변 여부, 프로세스 종결의 가역성이 미확인 상태다. 6.2절 1·2번 항목 참조.

#### 4.6.7. 현재 단계의 원본

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 환자 레코드가 현재 단계를 **문자열**(`감정평가 (사전)`)로 들고 있었다. 화면은 그 문자열을 프로세스 정의의 단계 이름과 **대조해** 번호를 찾았는데, 같은 종류의 노드가 둘인 정의(처방 → 수행 → 처방 → 수행)에서는 이름이 겹쳐 **언제나 앞의 것이 잡힌다.** 뒤쪽 노드에는 도달할 방법이 없고, 스테퍼는 환자가 뒤 회차를 돌고 있어도 앞 노드를 '진행 중'으로 칠한다 |
| 위반 원칙 | Safety and Trust — 화면이 환자의 실제 진행 지점과 다른 곳을 가리킨다 |
| 변경 전 | `patient.status` + `patient.nextStep` 두 문자열이 원본. `stepIndexOf`가 이름을 대조해 번호를 역산 |
| 변경 후 | **`patient.stepIndex`(단계 번호)가 원본이다.** 화면에 보이는 단계 이름과 다음 단계는 `statusOf` · `nextStepOf`가 정의에서 읽어 만든다 — 레코드에 문자열을 적어두지 않으므로 대조 자체가 사라진다 |
| 거부된 대안 | 노드마다 고유한 이름을 붙여 문자열이 겹치지 않게 한다 — 이름은 저작에서 사람이 짓는 값이라 같은 이름을 두 번 쓰는 것을 막을 수 없고, 막으면 '수행'을 두 번 도는 정의에 억지 이름을 붙이게 된다 |
| 검증 상태 | 내부 검토 (패널 · 리스트 · 배치 모달의 단계 표시, 단계 이동 후 스테퍼 반영을 DOM으로 확인) |

- **`status`는 표시용으로 남는다.** 우측 패널 · 전체 환자 리스트의 열 · `현재 단계` 분류 축 · 배치 모달의 진행 문구가 모두 `statusOf`를 부른다. 값을 **읽는 곳**은 그대로 두고 **드는 곳**만 없앤 것이다
- **프로세스가 붙지 않은 환자는 `접수 완료`다.** 0단계 이름(`프로세스 시작`)을 그대로 보이면 이미 시작한 것으로 읽힌다
- **다음 단계는 진행 중일 때만 있다.** 완료·중단 환자에게 다음을 적으면 아직 갈 곳이 남은 것으로 읽힌다
- 정의를 갈아끼워 단계 수가 줄면 저장된 번호가 범위를 넘을 수 있어 **끝 단계로 가둔다.** 없는 단계를 가리키면 스테퍼가 아무 노드도 현재로 칠하지 못한다

### 4.7. 효과성 분석

**웹 구버전 화면을 이식한 것이다.** 백엔드 분석 결과에 밀접하게 묶여 있어 **기능을 구현하지 않고 화면 구성만 옮겼다.**

프로그램·척도를 다루는 화면이므로 **우측 환자 패널이 없다**(4.0.1절). 여기서 세는 것은 환자 한 명이 아니라 연구 표본이고, 환자를 집어 오는 일도 없다.

구성은 다섯이다.

1. 머리 — 화면 이름 + **진단 전환**(게임과몰입 / PTSD) 세그먼트 토글
2. **인문학 프로그램 전후 효과성 분석** — 척도별 사전·사후 막대와 p값. 한 번에 셋씩 보고 화살표로 넘긴다
3. **전후 의과학적 효과성 검증** — HRV(자율신경) · fNIRS(전두엽 산소화) · 해석 결과
4. **생체신호 상관관계 분석** — 네 블록(HbO/HbR activation · RCI mean) 중 하나만 펼친다
5. **피어슨 상관계수 히트맵 · 유사도 · 대응표본 T-검정**

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 웹 화면은 상관계수 · 유의값 · 강조를 전부 파랑으로 칠한다 |
| 위반 원칙 | Consistency — accent 용법이 셋으로 동결돼 있다(3.1절) |
| 변경 후 | **값의 크기를 중립 명도 계단으로 나타낸다.** 진할수록 강한 상관이다. 유의한 p값은 색이 아니라 **굵기**로 올린다 |
| 부호를 색으로 말하지 않는 이유 | 음의 상관을 경고색으로 칠하면 '나쁨'으로 읽힌다. 부호는 숫자가 이미 말하고 있다 |
| 그 밖의 이식 결정 | ① 웹 상단의 상담사 카드를 걷었다 — 좌측 네비 하단에 이미 있다. ② 표가 가로로 길어 **표 안에서만 가로 스크롤**한다(페이지는 스크롤하지 않는다). ③ 네 블록을 다 펼치면 32행이라 하나만 펼친다 |
| 검증 상태 | 내부 검토 (DOM 확인 · 라이트/다크) |

- HRV는 지표마다 좋아지는 방향이 다르다(SDNN은 높을수록, LF/HF는 낮을수록). 방향을 보고 판정하되 **악화만 경고색**이다(3.1절)

**척도 구성은 앱의 감정평가 설문에서 온다.** 웹 화면은 PHQ-9 · BIS-11 · K-CAARS를 쓰지만, 그러면 같은 진단의 환자를 두 화면이 다른 척도로 말한다. 이름과 총점도 `surveys.js`에서 읽는다 — 인문 척도는 그 코드에 `H-`를 붙인 것이고, 기존 임상 척도는 접두 없는 원본이다.

> **확인 필요:** HRV·fNIRS 요약과 해석 문구는 웹 화면의 값을 옮겼고, 척도별 점수·상관·유사도·T-검정은 척도 코드를 해시해 만든 결정론적 임의값이다. 상관표의 HbO activation 한 블록만 웹 실측이다. 6.2절 36번 항목 참조.

### 4.8. 저작도구

Figma 디자인이 미완성이라 편집 화면은 설계하지 않았다. 이번에 확정한 것은 **일곱 도구의 이름**과 **저작도구 홈에서 각 도구로 들어가는 경로** 둘이다. 편집 화면의 구조가 확정되기 전에도 이 둘은 먼저 정해져야 한다 — 이름이 정해지지 않으면 좌측 네비도 홈도 무엇을 가리키는지 적을 수 없고, 들어가는 자리가 없으면 이후에 만드는 화면마다 진입 경로를 새로 정하게 된다.

- 프로그램/프로세스를 다루므로 **우측 환자 패널을 갖지 않는다**(4.0.1절).
- 저작도구는 1.3절의 그룹명 · 코드명 · 필드명 체계를 다루는 화면이다. 설문 코드는 코드명과 별도 네임스페이스이므로 두 체계를 한 입력란에서 받지 않도록 주의한다.

#### 4.8.1. 도구 이름

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 구버전 웹의 일곱 항목이 `저작`(프로그램 저작 · 세션활동 저작)과 `명세`(데이터 명세 · 프로세스 명세 · 문장 명세) 두 접미사를 나눠 갖는다. 그런데 저작도구 안은 전부 무언가를 만드는 화면이라 **접미사가 서로를 구분하지 못한다.** 무엇을 만드는지는 접미사 앞의 낱말이 이미 다 말하고 있다 |

> **확인 필요:** `도서 콘텐츠`라는 이름은 구버전 웹의 버튼(`새로운 도서 콘텐츠 등록`)을 근거로 정했는데, **실제 편집 단위는 도서가 아니라 그 도서에서 뽑은 문단 하나**다(4.8.10절). 이름과 단위가 어긋나 있고, 단위 자체가 확정되면 이름도 함께 본다. 6.2절 44번 항목 참조.

#### 4.8.2. 저작도구 홈

구버전 웹은 좌측 네비에 일곱 항목을 한꺼번에 펼쳐 두었다. 이 앱의 좌측 네비는 다섯 화면짜리 한 벌이라(2.3절 확정 치수) 여기에 일곱을 더 밀어 넣으면 네비가 화면의 절반이 된다. **들어가는 자리를 홈 하나로 모으고 네비는 `저작도구` 한 줄로 뒀다.**

- 구버전 웹의 두 묶음(데이터 / 프로그램)을 그대로 두고, 묶음마다 3열 카드로 편다
- **구버전 웹에서 무엇이 바뀌었는지는 화면에 적지 않는다.** 옛 이름을 카드에 함께 적는 안을 만들었다가 걷었다 — 쓰는 사람에게 필요한 것은 이 도구가 무엇을 만드는가뿐이고, 이름을 바꾼 사정은 만든 쪽의 일이다. 근거는 이 문서(4.8.1절)에만 남긴다
- **아직 만들지 않았다는 안내도 두지 않는다.** 같은 이유다. 목업이 있는 도구만 개수를 적고, 없으면 아무것도 적지 않는다 — **없는 것을 0으로 적지 않는다**(지웠다는 뜻으로 읽힌다)

#### 4.8.3. 도구 화면

**일곱 도구가 화면 하나를 공유한다.** 편집 화면의 구조는 도구마다 다를 것이 분명한데, 그것이 나오기 전에 일곱 벌을 따로 만들면 이후에 일곱 곳을 고쳐야 한다.

- 머리에 이름과 무엇을 만드는 화면인가를 둔다. 홈으로 돌아가는 길은 머리 왼쪽이다 — 네비에서 바로 들어올 수도 있어 뒤로가기에 기대지 않는다
- 그 도구가 지금 들고 있는 결과물을 **목록**으로 보여준다. 값은 각자의 목업(`surveys.js` · `processLibrary.js` · `programs.js`)에서 읽는다 — 저작도구가 자기 목록을 따로 들면 실제로 쓰이는 목록과 갈라진다
- **목록이 없는 도구는 카드 자체를 두지 않는다.** 빈 상자에 안내 문구를 채우면 그 문구가 화면의 내용이 된다
- **편집 화면은 도구마다 하나씩 열었다**(4.8.4~4.8.10절). 일곱 도구가 모두 자기 편집 화면과 목업을 갖는다

#### 4.8.4. 척도 저작 (편집 화면 1)

편집 화면은 **도구마다 하나씩, 축소 버전으로** 연다. 일곱을 한꺼번에 열면 확정되지 않은 구조를 일곱 번 추측하게 되고, 한 벌을 끝내 보기 전에는 무엇이 공통인지도 알 수 없다. 첫 대상은 **척도**다 — 앱이 이미 읽고 있는 값이 제일 많다.

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 구버전 웹의 저작 화면은 버전 · 스키마 버전 · 영문명 · 작성기관 · 문항수 · 역채점 · 서술형 · 중증도 구간까지 받는다. 그런데 **이 앱의 어느 화면도 그 값을 읽지 않는다** |
| 위반 원칙 | Minimalism — 읽는 곳이 없는 값을 받으면 입력한 사람이 반영됐는지 확인할 방법이 없다 |
| 변경 후 | **축소의 기준을 '앱이 실제로 쓰는 필드'로 둔다.** 설문 코드 · 이름 · 대상 · 역할 · 컷오프 · 설명 · 지시문 · 응답 보기 · 문항까지만 받는다. 읽는 곳이 생기면 그때 한 줄씩 는다 |
| 거부된 대안 | 구버전 폼을 그대로 옮긴다 — 태블릿 한 화면에 들어가지 않고, 받은 값의 절반이 아무 데도 쓰이지 않는다 |
| 검증 상태 | 내부 검토 (편집 → 저장 → 목록 반영 확인) |

- 뺀 것 중 둘은 이유가 따로 있다. **문항수**는 문항 목록이 이미 정한다(두 곳에서 받으면 갈라진다). **중증도 구간**은 이 앱의 등급 판정이 컷오프 하나와 핵심/보조로 갈리므로(4.6.3절) 구간을 여러 개 받아도 판정이 보지 않는다
- 분류 축은 **둘**이다. **증상**(공통 · 게임과몰입 · PTSD · 동반이환)과 **종류**(인문 · 임상). 종류는 효과성 분석이 이미 쓰던 구분이다 — 인문 척도는 임상 원본의 코드에 `H-`를 붙인 것이다(4.7절). 진단 축의 값은 `analysis.js`에서 온다
- **설문 코드는 새로 만들 때만 정한다.** 코드가 응답의 키(`환자:시점:코드`)라 나중에 바꾸면 이미 받아둔 응답이 끊긴다
- **총점은 저장할 때 다시 센다**(문항 수 × 보기 최고점). 저작한 척도와 목업으로 심어둔 척도가 같은 자를 써야 한다
- 오토세이브는 없다(3.6절). 저장은 버튼 하나이고, **미저장 이탈은 3버튼 경고**를 거친다 — 머리의 뒤로가기와 라우터 이탈이 같은 자리를 통과한다
- 저장할 수 없을 때는 **비활성 사유 콜아웃**이 무엇이 비었는지 말한다(3.8절)

#### 4.8.5. 데이터 필드 저작 (편집 화면 2)

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 구버전 웹은 좌측에서 필드 하나를 고르고 가운데 폼에서 그 하나만 고친다. 그런데 **코드명은 그룹 접두 + 순번**이라(1.3절) 필드 하나만 떼어 보면 그 번호가 어디서 온 값인지 보이지 않고, 고치는 동안 그룹 전체의 모습이 사라진다 |
| 위반 원칙 | Consistency — 화면의 편집 단위가 데이터의 단위와 어긋난다 |
| 변경 후 | **편집 단위를 그룹으로 올린다.** 좌측은 그룹 자체(코드 · 이름 · 분류), 우측은 그 그룹의 필드 표다. **코드명은 받지 않고 자리에서 만들어 보여준다** — 손으로 적게 하면 순서를 바꾸는 순간 둘이 갈라진다 |
| 거부된 대안 | ① 필드 낱개 편집(구버전) — 위 문제. ② 구버전 우측의 JSON 패널을 함께 둔다 — 폼과 같은 내용을 두 번 그리는 자리이고, 태블릿에서 JSON을 읽어 고칠 사람이 없다 |
| 검증 상태 | 내부 검토 (그룹 목록 → 편집 → 저장 → 목록 반영, 없는 그룹 진입 차단 확인) |

- 그룹 코드도 **만들 때만** 정한다. 이미 붙은 코드명이 전부 여기서 나오기 때문이다(척도의 설문 코드와 같은 이유)
- 유형이 `선택`일 때만 선택지 입력이 나온다. **고를 것이 없는 선택 필드는 빈 칸이 된다**
- 분류는 `기본정보` / `감정평가` / `생체신호` 셋이다 — 데이터 명세가 이 셋으로 탭을 나눈다
- **생체신호 두 그룹은 측정 화면과 같은 항목을 읽는다**(`bioSignals.js`). 같은 항목을 두 곳에 적으면 측정 화면과 저작도구가 다른 항목을 말하게 된다
- **감정평가 분류의 그룹(EA)은 설문 코드별 총점을 필드로 본 것이다.** 응답 한 줄 한 줄이 아니라 총점이 필드가 되는 이유는 **앱이 읽는 값이 그것**이기 때문이다 — 처방의 등급 판정도(4.6.3절) 종료 화면의 사전·사후 비교도(4.6.6절) 총점 하나만 본다. 문항 단위로 필드를 만들면 척도를 고칠 때마다 그룹의 필드 수가 흔들린다. 필드는 척도 목록에서 만들고 앞에 `평가 시점` · `평가일자` 둘을 둔다 — 총점만 있고 시점이 없으면 사전·사후가 한 칸에 겹친다

> **확인 필요:** 기본정보(DS) 14개는 구버전 웹 화면의 것을 옮겼고 단위·유형은 임의로 채웠다. **감정평가 그룹의 수집 단위(설문 코드별 총점)는 임의로 정한 것이다** — 구버전 웹에 해당 그룹이 없어 근거가 없다. 6.2절 4 · 39번 항목 참조.

#### 4.8.6. 프로세스 저작 (편집 화면 3 · MVP)

**프로세스의 단계 수는 정해져 있지 않다.** 감정평가 · 프로그램 처방 · 프로그램 수행 노드를 몇 개든, 어떤 순서로든 이을 수 있다 — 구버전 웹이 노드 편집기로 설계된 이유가 그것이다. 표준형(사전 평가 → 처방 → 수행 → 사후 평가)은 흔한 한 가지일 뿐이고, 처방과 수행을 번갈아 두 번 도는 프로세스도 성립한다.

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 구버전 웹은 자유 캔버스에서 노드를 끌어다 선으로 잇는다. 태블릿 터치로 연결선을 잇는 조작 자체가 무겁고, 좁은 화면에서 캔버스를 확대·이동하며 편집하기 어렵다 |
| 위반 원칙 | Efficiency — 조작의 무게가 만들려는 것(노드의 종류와 순서)에 비해 과하다 |
| 변경 후 | **노드 목록을 세로 시퀀스로 둔다.** 개수 제한 없이 추가 · 삭제하고 위아래로 옮긴다. 위에서 아래가 곧 진행 순서다 |
| 거부된 대안 | ① 단계를 표준형 넷으로 고정하고 내용물만 편집 — **프로세스의 실제 모델과 어긋난다.** 만들 수 있어야 할 흐름을 도구가 막는다. ② 자유 캔버스를 그대로 옮긴다 — 위 문제. 표현해야 할 것이 시퀀스 하나뿐이라 캔버스가 주는 것이 없다 |
| 검증 상태 | 내부 검토 (4노드 정의를 5노드로 늘려 저장 → 목록 반영 확인) |

- **감정평가 노드만 시점(사전 · 사후)을 갖는다.** 고르지 않으면 미연결이고, 같은 시점이 둘이면 저장을 막는다 — 사전·사후를 이름으로 찾는 화면들이(4.6.2 · 4.6.5절) 어느 노드를 봐야 할지 알 수 없다
- **회차는 정의가 적지 않는다.** 회차의 이름 · 개수는 처방된 프로그램이 정하고 **날짜와 간격은 일정이 정한다**(4.6.4절). `주 1회 · 5주` 같은 값을 정의가 약속하면 실제 일정과 어긋나는 순간 어느 쪽이 맞는지 알 수 없다. 목업 정의의 단계 메타에서도 주기 문구를 걷었다
- **생체신호는 토글 하나다.** 웹은 HRV · fNIRS를 따로 켜지만 앱이 읽는 값은 `bio` 하나뿐이라(측정 모달이 두 종류를 모두 연다) 나눠 받아도 반영될 자리가 없다 — 4.8.4절의 축소 기준 그대로다
- 증상을 바꾸면 **그 증상에서 고를 수 없는 설문은 선택에서 빠진다.** 남겨두면 그 증상에 없는 구성이 저장된다
- **처방 노드는 고르는 자리가 아니다.** 처방은 그 자리에서 상담사가 한다(4.6.3절). 대신 **그 증상에서 처방할 수 있는 프로그램을 읽기 전용으로 보여준다** — 이 노드에 이르렀을 때 무엇을 고르게 되는지 알아야 흐름을 짤 수 있다. 효과성이 가장 높은 하나에 `추천`이 붙되 그것도 읽는 값이다(**추천은 하나뿐이다** — 절반에 배지가 붙으면 추천이 아니라 분류가 된다)
- **처방 · 수행 노드는 정의에 내용을 남기지 않는다.** 프로세스 상세 모달에서도 '등록된 항목이 없습니다'가 아니라 **무엇이 그 자리를 정하는지**를 적는다 — 빠뜨린 것처럼 읽히면 안 된다

- **프로세스 시작과 종료는 저작에서 다루지 않는다.** 프로세스를 붙이고 끝내는 고정된 양끝이고, 코어 프로세스가 이미 두 화면을 갖고 있다(4.6절)
- **코어 프로세스도 정의의 노드에서 단계를 만든다**(4.6절). 저작에서 노드를 늘리면 그 정의를 쓰는 환자의 스테퍼가 그대로 따라간다

#### 4.8.7. 데이터 명세 저작 (편집 화면 4)

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 명세는 '무엇을 수집할지'를 정하는 자리인데, 필드의 이름 · 유형까지 여기서 고칠 수 있으면 **같은 값을 고치는 자리가 둘**이 된다. 어느 쪽이 원본인지 알 수 없고 한쪽만 고쳐진다 |
| 위반 원칙 | Consistency — 한 값의 원본은 한 곳이어야 한다 |
| 변경 후 | **명세는 필드를 만들지 않고 고른다.** 필드 저작(4.8.5절)이 원본이고, 명세는 **코드명으로 가리키기만** 한다. 화면에도 이름·유형을 고치는 입력이 없고 어디서 고치는지만 적는다 |
| 거부된 대안 | 명세 안에서 필드를 새로 만들 수 있게 한다 — 위 문제. 그룹에 속하지 않은 필드는 코드명을 받을 자리도 없다 |
| 검증 상태 | 내부 검토 (필드 해제 → 저장 → 목록의 필드수 반영 확인) |

- **명세는 그룹 하나에 붙는다.** 코드명이 그룹 접두 + 순번이라 여러 그룹을 한 명세에 섞으면 같은 순번이 두 번 나온다. 여러 그룹이 필요하면 명세를 나눈다
- **분류(기본정보 · 감정평가 · 생체신호)는 그룹이 정한다.** 명세가 따로 들면 생체신호 그룹을 담은 '기본정보 명세' 같은 어긋난 조합이 만들어진다
- 그룹을 바꾸면 고른 필드는 **비운다.** 다른 그룹의 코드가 남으면 없는 필드를 가리킨다
- 이름이 겹치는 것은 막지 않고 알린다 — 구버전 웹도 같은 이름의 `기본명세`를 기관마다 하나씩 두고 있다

> **확인 필요:** 구버전 웹 카드에서 확인할 수 있는 것은 요약 줄(이름 · 버전 · 증상 · 필드수 · 생성일 · 기관 · 작성자)뿐이라, **어떤 필드가 담기는지는 임의로 채웠다**(그룹의 필드를 그대로 담았다). 버전 · 작성자는 앱이 읽는 곳이 없어 받지 않는다(4.8.4절의 축소 기준). 6.2절 4번 항목 참조.

#### 4.8.8. 프로그램 저작 (편집 화면 5)

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 프로그램은 회차의 이름과 개수를 정하는 원본인데(4.6.4절) 그것을 만드는 자리가 없었다. 한편 회차 **안**의 PHASE와 활동까지 여기서 만들면 세션 활동 저작과 같은 것을 두 화면이 만들게 된다 |
| 위반 원칙 | Consistency — 한 값의 원본은 한 곳이어야 한다 |
| 변경 후 | **회차의 이름과 순서, 그리고 무엇을 붙일지까지가 이 화면의 몫이다.** 회차 안의 내용은 세션 활동이 만들고(4.8.9절) 여기서는 **고른다** — 데이터 명세가 필드를 만들지 않고 고르는 것과 같은 자리다(4.8.7절). 프로그램 자체(이름 · 증상 · 분야 · 운영형태 · 기관 · 지역 · 분량 · 감정 · 주제어 · 준비물 · 설명)와 회차 시퀀스(추가 · 이름 · 활동 · 위아래 이동 · 삭제)를 받는다 |
| 거부된 대안 | 회차 안의 PHASE 다섯까지 여기서 편집한다 — 세션 활동 저작이 만들 자리와 겹치고, 한 화면에서 프로그램 · 회차 · PHASE · 활동 네 겹을 편집하게 된다 |
| 검증 상태 | 내부 검토 (회차 이름 변경 → 저장 → 목록 · 프로그램 처방의 세션 상세에 반영되는 것을 DOM으로 확인) |

- **효과성(`rating`)은 받지 않는다.** 수행 기록에서 나오는 값이지 만드는 사람이 정하는 값이 아니다. 축소 기준은 척도 저작(4.8.4절)과 같되, **저작이 정하는 값이 아닌 것**을 하나 더 뺀 것이다
- **새 프로그램의 효과성은 `-`다.** 0으로 두면 '효과가 없다'는 측정 결과로 읽힌다
- **회기 수 · 분량을 설명에 적게 하지 않는다.** 회차 목록이 이미 개수를 정하고 분량은 자기 칸이 있다 — 설명에 다시 적으면 회차를 늘렸을 때 설명만 낡는다
- 기관과 지역을 나눠 받는다. 목업이 `기관 · 지역`을 한 문자열로 들고 있었는데, 그러면 기관 이름이 두 자리에 적힌다
- **회차 하나 = 이름 + 붙인 활동**(`activityId`)이다. 붙으면 세션 상세가 그 활동의 치유단계를 그대로 읽고, 붙지 않은 회차만 생성기가 골격으로 채운다
- **고를 수 있는 것은 `작성 완료`된, 같은 증상의 활동뿐이다.** 덜 채워진 활동이 붙으면 환자를 만나는 자리에 빈 안내문이 오르고, 증상이 다른 활동은 이 프로그램이 다루는 것과 어긋난다
- 증상을 바꾸면 **그 증상에서 붙일 수 없게 된 활동은 떨어진다** — 프로세스 저작이 설문을 떨어뜨리는 것과 같다(4.8.6절). 이미 붙어 있는 활동은 선택지에 남긴다(빠지면 무엇이 붙어 있었는지 화면에서 사라진다)
- 회차 삭제는 **확인을 거친다**(3.6절). 이름도 활동도 없는 빈 줄만 확인 없이 지운다

#### 4.8.9. 세션 활동 저작 (편집 화면 6)

구버전 웹 '세션활동 저작' 화면을 옮긴 것이다. 좌측 **세션활동 메타데이터**, 우측 **블록 구성** 두 판이다.

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 프로그램은 회차의 이름과 순서만 정한다(4.8.8절). **회차 안에서 무엇을 하는가**를 만드는 자리가 없어, 세션 상세의 PHASE·활동을 `programs.js`의 생성기가 골격으로 채우고 있었다 |
| 위반 원칙 | Consistency — 화면이 보여주는 내용에 원본이 없다 |
| 변경 후 | **세션 활동이 자기 목업(`activities.js`)을 갖는다.** 활동 하나는 치유단계(도입 · 투사 …) 여럿이고, 단계마다 블록이 여럿이며, 블록은 **활동 종류 하나 + 내용 하나**다. 블록은 `안내문`(치유사가 읽어 주는 말)과 `인문 문장`(인용하는 원문) 둘로 갈리는데, **안내문은 적고 인문 문장은 고른다**(4.8.10절) |
| 거부된 대안 | 프로그램 저작 안에서 회차 내용을 함께 편집한다 — 한 화면에서 프로그램 · 회차 · 단계 · 블록 네 겹을 편집하게 되고, 활동을 여러 프로그램이 나눠 쓰는 길도 막힌다(웹의 `프로그램 세션에 배치 가능`이 그 관계를 전제한다) |
| 검증 상태 | 내부 검토 (블록 본문 수정 → 저장 → 목록·재진입 반영, 단계/블록 삭제 확인, 본문 881 · 좌 300 / 우 573) |

- **좌우로 나눈 것은 웹의 사정이 아니라 이 일의 사정이다.** 블록 문구를 쓰는 동안 대상과 소요시간이 화면에서 사라지면 안 된다 — 프로그램 처방을 탭 둘로 둔 것과 같은 이유다(4.6.3절)
- **인문 활동 종류는 받지 않는다.** 블록마다 이미 고르는 값이라 위에서 또 고르면 두 곳이 갈라지고, 블록이 여럿인 활동에서는 위의 값이 어느 블록을 가리키는지도 알 수 없다
- **치유 구성요소 · 주제어 · 증상의 강도 · 치유대상 연령대도 뺐다.** 읽는 화면이 없다(4.8.4절의 축소 기준). **치유대상 감정만 남긴 것은 세션 상세가 그 값을 보여주기 때문이다**(4.6.3절)
- 머리의 `초기화` · `미리보기`도 두지 않았다. 초기화는 미저장 되돌리기인데 이 앱은 그것을 이탈 경고로 처리하고(3.6절), 미리보기는 아직 볼 화면이 없다
- `작성 완료 (프로그램 세션에 배치 가능)`는 남겼다. **배치할 수 있는 상태인가**는 앱이 읽을 값이다 — 목록에서 아직 아닌 것에 `작성 중` 배지가 붙는다
- **인문 문장 블록은 적는 자리가 아니라 고르는 자리다.** 인용하는 원문의 원본은 도서 콘텐츠이고, 블록은 **도서 id + 문장 번호**로 가리키기만 한다 — 문장을 옮겨 적으면 같은 문장이 자리마다 다시 적히고 어느 책 몇 쪽에서 온 것인지도 남지 않는다. 데이터 명세가 필드를 고르는 것과 같은 자리다(4.8.7절)
- **도서를 바꾸면 고른 문장은 비운다.** 문장 번호는 그 문단 안에서만 뜻이 있어, 남겨두면 다른 문단의 엉뚱한 문장을 가리킨다(데이터 명세가 그룹을 바꿀 때와 같다)
- **무엇이 채워진 블록인가는 종류가 정한다**(`blockFilled`). 안내문은 본문이, 인문 문장은 고른 문장이 있어야 채워진 것이다
- **안내문 본문은 여러 줄이 될 수 있다.** 줄 하나가 세션 상세의 절차 한 줄(a · b · c)이 된다 — 절차마다 블록을 나누면 같은 활동 종류가 여러 번 되풀이된다
- 단계·블록 삭제는 **확인을 거친다**(3.6절). 내용이 빈 것만 확인 없이 지운다. 저장할 때도 빈 블록과 블록이 하나도 없는 단계는 걷는다 — 내용이 없는 자리는 치유사가 읽을 것이 없다

**배치는 프로그램 저작의 회차 행에서 한다**(4.8.8절). 회차가 `activityId`를 들고, 세션 상세가 붙은 활동의 치유단계를 그대로 읽는다 — 단계의 개수도 활동이 정한다. 다섯으로 고정하면 세 단계짜리 활동을 붙여도 화면이 다섯 칸을 그려 두 칸이 지어낸 값이 된다. **`작성 완료`가 배치의 자격이다.**

**필요 도구는 자유 입력이다.** 웹은 고정 체크박스 여덟(연필 · 물감 · 색연필 · 도화지 · 가위 · 풀 · 노트 · 포스트잇)이지만, 붙은 활동의 준비물이 세션 상세에 그대로 오르는데 프로그램 쪽 준비물이 자유 입력이라 두 목록이 갈렸다. **같은 자리에 오르는 값은 같은 자를 써야 한다** — 고정 목록에 없는 물건(시 선집 · 워크북)을 적을 길도 함께 생긴다.

> **확인 필요:** 치유단계 유형은 웹 화면에서 `도입` · `투사` 둘만 확인했고 나머지 셋(`통찰` · `통합` · `마무리`)은 임의로 채웠다. 프로그램의 PHASE 이름(도입 · 전개 · 심화 · 정리 · 마무리)과 같은 축인지도 확정되지 않았다 — 활동이 세션에 배치되면 이것이 PHASE 자리에 들어간다. 6.2절 43번 항목 참조.

#### 4.8.10. 도서 콘텐츠 저작 (편집 화면 7)

구버전 웹 '문장 명세' 화면을 옮긴 것이다. 좌측 **기본 정보**, 우측 **추출 문장 속성값** 두 판이다.

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 프로그램의 `인문 문장` 블록(4.8.9절)이 인용할 원문을 **직접 적게** 되어 있었다. 같은 문장을 여러 활동이 쓰면 자리마다 다시 적히고, 어느 책 몇 쪽에서 온 문장인지도 남지 않는다 |
| 위반 원칙 | Consistency — 한 값의 원본은 한 곳이어야 한다 |
| 변경 후 | **한 건 = 한 도서에서 뽑은 문단 하나다.** 작품을 특정하는 서지 정보(작품명 · 유형 · 출판사 · 출판연도 · 저자 · 출생연도)와 뽑은 자리(추출 페이지 · 추출 문단), 그리고 그 문단에 붙는 **45개 속성값**으로 이루어진다 |
| 거부된 대안 | 속성 45개를 화면에 칩으로 직접 적는다 — 항목이 하나 늘 때마다 화면을 고쳐야 한다. 구성이 가장 먼저 바뀔 값이라 목업의 배열에서 그린다 |
| 검증 상태 | 내부 검토 (축 접기 · 값 토글 → 개수 반영 → 저장 → 목록 반영, 본문 881 · 좌 320 / 우 553) |

- **여기서는 필드를 줄이지 않았다.** 앞의 여섯 화면은 '앱이 읽는 필드만'으로 좁혔지만(4.8.4절), 이 화면의 왼쪽은 전부 **작품을 특정하는 서지 정보**라 하나만 빠져도 어느 책의 몇 쪽인지 가리키지 못한다
- 뺀 것은 머리의 `DCAT 데이터셋` 하나다. 입력이 아니라 표준 형식으로 **내보내는** 자리이고 지금 붙일 곳이 없다
- **속성 분류는 화면이 들지 않는다**(`BOOK_ATTRIBUTES`). 축 다섯 · 소분류 열둘 · 항목 45의 구성은 백엔드와 연구 방향에 따라 가장 먼저 바뀔 값이라, 화면은 배열을 그리기만 한다 — 축을 더하거나 항목을 갈아끼우는 일이 목업 한 곳에서 끝난다. 머리의 `45개 항목`도 세어서 낸다
- **축은 접힌다.** 45개가 한 번에 펼쳐져 있으면 지금 보는 축을 잃는다. 머리와 본문은 한 상자다(3.4절)
- 소분류가 없는 축(관계 · 주제어)은 **이름 줄을 두지 않는다.** 하나뿐인 묶음에 이름을 붙이면 없는 층이 하나 더 있는 것처럼 보인다
- 저장할 때 **분류에서 사라진 값은 걷는다.** 속성 목록을 갈아끼웠을 때 없는 항목을 붙들고 있으면 그리지도 못하는 값이 개수에만 남는다

> **확인 필요:** 같은 도서에서 문단을 여럿 뽑으면 **작품 정보가 건마다 되풀이된다.** 도서 하나 아래 발췌 여럿으로 묶는 편이 값의 원본을 한 곳에 두는 길이지만, 백엔드가 어느 단위로 내려줄지 확정되지 않아 웹의 등록 단위를 유지했다. 6.2절 44번 항목 참조.

**문장은 문단에서 끊어 낸다. 따로 저장하지 않는다.** 세션 활동의 `인문 문장` 블록이 **도서 id + 문장 번호**로 가리키고, 문장 자체는 읽을 때 문단에서 만든다 — 문장을 복사해 두면 문단을 고쳤을 때 블록만 옛 문장을 계속 말한다.

- 끊는 규칙은 **마침표 · 물음표 · 느낌표 다음의 공백**이다
- **문단이 짧아져 번호가 범위를 넘으면 그 사실을 말한다**(`가리킨 문장을 찾을 수 없습니다`). 없는 문장을 지어내지 않는다

**문단을 고치면 저장하기 전에 알린다.** 문장이 하나 늘거나 줄면 뒤쪽 번호가 밀려, 그것을 가리키던 블록이 다른 문장을 말하게 된다. 번호가 범위를 넘는 경우는 읽는 화면이 알아채지만(`가리킨 문장을 찾을 수 없습니다`) 밀린 경우는 조용히 바뀌기 때문이다.

- **막지 않고 알린다.** 고쳐야 할 오타일 수도 있다 — 진단 불일치 경고(4.6.1절)와 같은 자리다
- 어느 활동의 어느 단계가 몇 번째 문장을 가리키는지 **목록으로 보여준다.** 개수만 말하면 저장한 뒤 어디를 확인해야 할지 알 수 없다
- **문단을 고쳤을 때만 묻는다.** 속성값만 바꾼 저장까지 붙들면 경고가 값을 잃는다
- 갈림길이라 스크림 탭으로 닫지 않는 alert이고, `돌아가기`는 고치던 폼 그대로다(중복 경고와 같은 문법)

> **확인 필요:** 문장을 끊는 규칙은 임의로 정한 것이다. 인용부호 안의 마침표나 줄임표는 갈라진다. 6.2절 45번 항목 참조.

#### 4.8.11. 즐겨찾기와 홈의 '빠른 저작'

| 필드 | 내용 |
| --- | --- |
| 문제 정의 | 홈의 '빠른 저작' 네 칸이 **고정 목록**이었고 눌러도 가는 곳이 없었다. 이름도 저작도구의 것과 갈라져 있었다(데이터 항목 · 평가 척도 · 발췌문 · 프로세스 설계). 한편 자주 고치는 항목 하나에 닿으려면 네비 → 저작도구 홈 → 도구 → 목록 → 행으로 네 번을 눌러야 한다 |
| 위반 원칙 | Consistency (같은 것을 두 이름으로 부른다) · Efficiency (자주 가는 자리가 가장 멀다) |
| 변경 전 | 고정 4칸. 아무 동작 없음 |
| 변경 후 | **즐겨찾기의 단위는 도구다.** 도구 화면(4.8.3절) 머리 우측의 별표로 담고, 홈의 '빠른 저작'이 그것을 편다. 칸을 누르면 그 도구로 바로 간다. 머리(`빠른 저작` + chevron) 전체가 저작도구 홈으로 가는 길이다 — 우측 패널의 `전체 환자` 머리와 같은 문법이다(4.0.5절) |
| 거부된 대안 | ① 일곱 도구를 홈에 그대로 편다 — 좌측 컬럼 폭이 247이라 일곱 칸이 작업 목록을 밀어낸다. '자주 쓰는 것'과 '전부'는 다른 목록이다. ② **즐겨찾기의 단위를 항목(척도 하나 · 프로그램 하나)으로 둔다** — 홈에 이름이 긴 항목이 올라 칸이 두세 줄로 늘고, 무엇보다 저작에서 자주 하는 일은 '그 도구로 다시 들어가는 것'이지 '같은 항목을 다시 여는 것'이 아니다 |
| 검증 상태 | 내부 검토 (별표 → 홈 반영 → 해제 → 빈 상태까지 DOM으로 왕복 확인. 칸 106×60 · 2열) |

- **이름을 저장하지 않는다.** 도구 키만 남기고 이름·아이콘은 그릴 때 도구 정의에서 읽는다 — 복사해 두면 도구 이름을 바꿨을 때 홈만 옛 이름을 계속 말한다(4.8.1절에서 실제로 한 번 바꿨다)
- **칸의 모습은 그대로다.** 아이콘 24 + 이름 한 줄, 2열. 바뀐 것은 **무엇이 그 자리에 오는가를 쓰는 사람이 정한다**는 것뿐이다
- **별표에 accent를 쓰지 않는다.** accent 용법은 셋으로 동결돼 있고(3.1절), 채움과 글자색 한 단계로 충분히 갈린다
- **넷까지다.** 일곱을 전부 담으면 칸이 네 줄이 되어(336 vs 196) 그 아래 작업 목록이 밀려난다 — '자주 쓰는 것'을 고르는 자리가 '전부'가 되면 고른 의미도 없어진다
- **자리가 없으면 사유를 말한다**(3.8절). 다섯 번째 별을 누르면 아무 일도 일어나지 않는데 무반응은 고장으로 읽힌다. 콜아웃 둘째 줄이 뚫는 방법을 말한다 — 다른 도구의 별을 먼저 뺀다
- **빼는 것은 언제나 된다.** 가득 찬 상태에서 뺄 수 없으면 갈아끼울 길이 없다
- 별표가 하나도 없으면 빈 칸을 남기지 않고 **어디서 담는지 한 줄로 말한다**

> **확인 필요:** 즐겨찾기는 실제로는 사용자 계정에 붙는 값이다. 지금은 메모리에만 있어 새로고침하면 기본값 넷으로 돌아간다. 저장 위치가 정해지면 `mocks/favorites.js` 한 곳만 바꾼다. 6.2절 40번 항목 참조.

> **확인 필요:** 나머지 두 도구(세션 활동 · 도서 콘텐츠)의 편집 화면은 미착수다. 둘 다 **정의 목업부터** 만들어야 한다. 6.2절 4번 항목 참조.

> **미해결:** 저작도구 화면 설계에 필요한 데이터 구조 및 편집 범위가 미확인 상태다. 세션 활동 · 도서 콘텐츠의 목업은 이 확인 이후로 미룬다. 6.2절 4번 항목 참조.

### 5.2. 구조 개요

**레이아웃 규칙**

- 루트 높이는 뷰포트 기준 단위를 쓴다. **고정 px 높이를 금지한다** — 주소창 유무와 소프트 키보드로 높이가 변한다(2.3.2절).
- 3분할 셸은 좌우 패널 고정 폭 + 축소 금지, 중앙은 남는 폭을 차지한다.
- 스크롤은 각 패널 내부에서만 발생한다. 페이지 전체 스크롤을 금지한다.

**단일 원본 원칙**

| 데이터 | 원본 |
| --- | --- |
| 환자 명단 | 목업 파일 한 곳. 우측 패널의 최근 환자·전체 환자도, 분석 화면의 집계도 여기서 파생 |
| 환자 일정 | 목업 파일 한 곳. 날짜 키로 관리하며 아젠다와 캘린더가 같은 데이터를 본다 |
| 작업 | 목업 파일 한 곳. 타임라인의 업무 블록이 여기서 파생 |

**화면별 목업을 따로 두지 않는다.** 두 곳에 두면 한쪽만 갱신되어 화면이 갈라진다(3.7절).

**공유 가변 상태는 두 개로 제한한다.** 늘리기 전에 재검토한다.

| 상태 | 책임 |
| --- | --- |
| 드래그 상태 | 꾹 누르기·드래그. 배치로 끝난 제스처의 click 삼킴 포함(4.0.2절) |
| 일정 상태 | 환자 일정과 작업의 유일한 가변 상태. 화면이 사본을 들면 아젠다에서 배치한 일정이 캘린더에 보이지 않는다 |

**컴포넌트 추출 기준** — 조기 컴포넌트화를 금지한다. 화면을 인라인으로 먼저 작성하고, 두 번째 화면에서 반복이 확인된 것만 추출한다. 현재 추출된 것:

| 컴포넌트 | 책임 |
| --- | --- |
| 모달 셸 | 스크림·레이아웃·history 처리 (3.5절). modal / alert 두 형태를 갖되 history는 한 벌 |
| 일정/작업 입력 모달 | 배치 확인 · 일정 추가 · 작업 추가. **중복 경고와 단계 검증이 이 안에만 있어야** 화면별 우회 경로가 생기지 않는다 |
| 작업 상세 모달 | 설명 · 완료 · 완료 취소 |
| 미저장 이탈 경고 | 3버튼 경고(3.6절). 대상 문구만 받아 다른 화면에서도 그대로 쓴다 |
| 삭제 확인 | 복구 불가 문구 + 대상 특정. 메모와 일정이 같은 틀을 쓴다 |
| 일정 상세 | 환자 일정 한 건. 환자 상세로 가는 행 + 편집 · 삭제 |
| 비활성 사유 콜아웃 | 두 줄 경고(3.8절). 아젠다와 캘린더가 같은 것을 쓴다 |

**환자 일정에는 id를 붙인다.** 편집·삭제가 한 건을 특정해야 하는데 이름과 시간으로 찾으면 같은 날 같은 환자를 두 번 만나는 경우에 갈린다. 업무 블록은 작업에서 파생하므로 원본 작업의 id를 그대로 쓴다.

**스테퍼의 단계 판정은 목업 모듈 한 곳에 있다.** 환자 상세의 큰 스테퍼와 코어 프로세스의 컴팩트 스테퍼가 같은 함수를 부른다. 두 화면에 같은 로직을 복제해 두었더니 '시작 전 환자가 어느 단계도 열 수 없는' 결함이 양쪽에 똑같이 생겼고, 한쪽만 고치면 다시 갈라진다.

**목업 명단에는 프로세스·감정평가 응답·처방이 심어져 있다.** 명단 원본에는 이름·진단·현재 단계밖에 없어 화면을 열면 프로세스가 '미할당', 설문이 전부 '작성하기', 등급이 전부 '미작성'으로 비어 보였다. 별도 모듈이 앱 시작 시 한 번 채우며, **값은 결정론적이다**(환자 id를 해시해 씨앗으로 쓴다) — 새로고침마다 점수가 달라지면 화면을 실측으로 검증할 수 없고 같은 환자가 두 번 다른 사람이 된다. **채우는 범위는 현재 단계가 정한다** — 지나온 단계만 값이 있고, 지금 단계는 일부만 있거나 비어 있으며, 아직 오지 않은 단계는 손대지 않는다. 실제 데이터가 오면 이 모듈만 걷어내면 된다.

**환자 명단은 반응형이다.** 프로세스 개시(4.6.1절)에서 환자의 프로세스 상태·현재 단계·다음 단계가 바뀌는데, 스테퍼 · 우측 환자 패널 · 분석 화면 · 전체 리스트가 모두 같은 명단 하나를 본다. 명단이 평범한 배열이면 할당 결과가 그 자리에서 갱신되지 않고, 화면마다 사본을 두면 진행 상태가 갈린다. 명단이 하나뿐이므로 목업 모듈 한 곳만 감쌌다.

**메모는 공유 상태로 올리지 않았다.** 환자 상세 화면 하나에서만 쓰이므로 위 두 상태에 합류시키지 않고, 목업 모듈이 반응형 배열을 직접 들고 있다. 모듈이 싱글턴이라 화면을 나갔다 와도 편집 결과가 남는다.

### 5.3. 구현 범위 및 미구현 항목

**구현 완료**

- 환경 셋업, 토큰 이식, 3분할 셸 + 라우터(5화면), 좌측 내비게이션 전체
- 홈(업무): 빠른 저작 · 작업(정렬 · 완료 아코디언) · 일정 타임라인 + 날짜 이동
- 작업 상세 모달(설명 · 완료 · 완료 취소 · **삭제**), 아젠다 행 탭 인터랙션
- 우측 환자 패널 (환자 화면에만. 탭하면 환자 상세로 이동). **전체 환자 머리 → 리스트 진입 · 정렬(가나다순 / 최근 진료순 / 진단순) · 환자 검색** (4.0.5절)
- 꾹 누르기 → 드롭 상태 → 고스트 → 확인 모달 → 배치. **환자와 작업 모두, 아젠다와 캘린더 모두**
- 모달 통합(배치 확인 · 일정 추가 · 작업 추가) + 중복 경고 + 날짜/시간 선택
- 일정 화면: 월 그리드 + 날짜 팝오버 + 날짜 드롭 + 빈 칸 탭 → 일정 추가
- 모달 환자 리스트 2구간, 업무 날짜·시간 '미정'
- 환자 분석: KPI · 필터 칩 · 프로세스/진단/연령/성별 차트
- 전체 환자 리스트: 검색 · 필터/정렬 · 칩 · 표 · 빈 상태. KPI에서 필터를 물고 온다
- 환자 상세: 정보 · 스테퍼 · 프로세스 히스토리 · 핵심 지표(추이 그래프). 네 진입 경로 연결. **프로세스 진입 버튼(프로세스 시작 / 이어하기 / 프로세스 재시작)** (4.5.1절)
- 개인 메모 탭: 목록 · 검색 · 새 메모 · 편집 · 삭제 확인 · 미저장 이탈 경고(3버튼)
- 환자 분류 축 `현재 단계` (리스트 필터 · 패널 정렬/검색). 분석 차트에는 올리지 않는다
- 일정 편집·삭제: 일정 상세 모달 → 편집(날짜·시간·유형) · 삭제 확인. 아젠다와 캘린더 양쪽
- 좌측 하단 프로필 사진(자산 파일이 있으면 쓰고, 없으면 이름 첫 글자로 대체)
- 코어 프로세스 공통 셸(환자 정보 + 컴팩트 스테퍼 + 환자 상세 복귀)
- **코어 프로세스 0단계 '프로세스 개시'**: 치유 프로세스 리스트(진단 칩 · 검색 · 정렬 · 표 · 구버전 표기) → 상세 모달(단계 아코디언) → 할당 확인 → 할당. 진단 불일치 경고 포함 (4.6.1절)
- **코어 프로세스 1·4단계 '감정평가'**: 사전/사후 시점 칩 · 설문 카드(핵심·보조 배지, 점수 막대와 컷오프) · 작성하기/작성완료 · 다음 단계 CTA (4.6.2절)
- **코어 프로세스 3단계 '프로그램 수행'**: 회차 목록(진행률 · 상태 배지 셋) · 회차 상세 · 수행 내역 기록 · 저장 후 다음 회차 (4.6.4절)
- **코어 프로세스 2단계 '프로그램 처방'**: 감정평가 정보 탭(등급 배지 · 감정 지표 막대) · 프로그램 선택 탭(검색 · 정렬 · 필터 넷 · 행) · 프로그램 상세 ↔ 세션 상세 모달(PHASE 페이지 넘김) (4.6.3절)
- **코어 프로세스 5단계 '프로세스 종결'**: 요약 네 칸 · 감정평가 사전·사후 비교 카드 · 종료 시각 · 출력. 종결 조작 자체는 4단계의 `종료 확정`이다 (4.6.5 · 4.6.6절)
- **프로그램 저작(편집 화면 5)**: 프로그램 정보 + 회차 시퀀스(추가 · 이름 · 이동 · 삭제 확인) (4.8.8절)
- **세션 활동 저작(편집 화면 6)**: 좌 메타데이터 + 우 블록 구성(치유단계 → 블록 → 활동 종류 · 본문). 활동 정의 목업 신설 (4.8.9절)
- **프로그램 회차 ↔ 세션 활동 배치**: 회차가 활동을 가리키고 세션 상세가 그것을 읽는다. 필요 도구는 자유 입력으로 통일 (4.8.8 · 4.8.9절)
- **도서 콘텐츠 저작(편집 화면 7)**: 좌 기본 정보 + 우 추출 문장 속성값(축 다섯 · 45개 항목, 목업이 구성을 든다). 도서 목업 신설 (4.8.10절)
- **붙지 않은 회차의 빈 상태**: PHASE 생성기를 걷고 세션 상세 · 프로그램 수행이 `활동이 없다`고 말한다 (4.6.3절)
- **문단 수정 시 인용 경고**: 도서의 문단을 고치면 그 문장을 가리키는 블록을 목록으로 보여주고 확인을 거친다 (4.8.10절)
- **인문 문장 ↔ 도서 콘텐츠 연결**: 블록이 도서 id + 문장 번호로 가리키고 세션 상세가 문단에서 읽어 온다 (4.8.9 · 4.8.10절)
- **저작 즐겨찾기 ↔ 홈의 빠른 저작**: 도구 화면 머리의 별표로 담고 홈이 편다(단위는 도구). 머리 전체가 저작도구 홈으로 가는 길 (4.8.11절)
- **감정평가 분류의 데이터 그룹(EA)**: 설문 코드별 총점 + 시점 · 일자. 같은 분류의 데이터 명세도 한 건 추가 (4.8.5절)
- **환자의 현재 단계를 단계 번호로 전환**: `status` 문자열 대조를 걷고 `stepIndex`를 원본으로 (4.6.7절)
- **설문 수행 화면**: 셸 전체를 걷은 환자용 화면. 문항 표 · 진행률 · 임시 저장 · 제출 · 뒤로가기 경고 · 완료 알림 화면 (4.0.1 · 4.6.2절). Figma 없이 임의 제작

### 6.3. 후속 작업 시 활용 방안

`[작성 예정]`

**미착수 화면 설계 시 적용 절차**

1. 2.1절 원칙 위계와 3장 전역 규칙을 먼저 확인한다. 3장의 규칙은 화면과 무관하게 적용된다.
2. 4.0절의 화면 구조 공통(패널 유무 · 행 인터랙션 · 배치 문법 · 모달)에서 해당 화면이 어디에 속하는지 판정한다.
3. 6.2절에서 그 화면과 관련된 미해결 항목을 먼저 해소한다. 특히 1·2번은 코어 프로세스 착수 전 확인이 필요하다.
4. 새로운 설계 결정은 4장 템플릿으로 기록하고, 거부한 대안을 반드시 함께 남긴다.

**환자용 화면 설계 착수 시 재검토가 필요한 결정**

환자용 화면은 상담사용 구현이 마무리되는 시점에 병행 착수한다(1.2절). 구현 대상 화면 수가 적고 3장 전역 규칙을 그대로 이어받으므로, 새로 판단해야 하는 것은 다음뿐이다.

- **4.6.2절 설문 수행 화면이 선례다.** 환자가 조작하는 화면의 셸 구성·이탈 차단 방식이 이미 확정되어 있으므로, 환자용 화면 전반의 기준으로 삼는다
- 6.2절 6번 — 설문 화면 외의 대면 상황에서 타 환자 정보를 어떻게 다룰지
- 터치 타겟 규격 — 환자 연령대에 따라 기본값 상향 검토 필요 (3.3절)
- 모바일 대응 — 3분할 셸이 성립하지 않으므로 2.3.2절 랜드스케이프 고정 전제가 깨진다. 환자용 화면은 셸을 쓰지 않는 구성이 기본이므로 영향은 제한적일 것으로 예상

**기존 웹 개선 작업 시 참조 가능한 항목**

- 3.1절 색상 운용 규칙 — 입력 매체와 무관하게 적용 가능
- 3.6절 저장 상태 및 데이터 보호 규칙 — 2.2절 평가에서 도출된 구조적 이슈에 직접 대응
- 3.7절 파생 데이터 산출 규칙 — 동일 사실의 이중 저장 문제
